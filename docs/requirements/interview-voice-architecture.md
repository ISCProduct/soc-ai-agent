# AI面接 音声基盤 要件定義書

Issue: #1193

## 1. 目的

AI面接の音声基盤について、**Realtime API 実装を有効化するか、削除して Turn 経路に一本化するか**を決定する。

あわせて、実際に使われている経路のコストを計測できる状態にする。

本書では、現状の事実、判断軸、選択肢とその影響、受け入れ条件を定義する。技術的な実装方法は Design Doc (`docs/design/interview-voice-architecture.md`) に分離する。

## 2. 背景

本番インフラのコスト調査の過程で、AI面接に3つの問題が判明した。いずれも実害はあるが、稼働日が限られており可観測性が無いため、誰も気づいていなかった。

1. Realtime API 実装が、モデルもエンドポイントも廃止済みで動作しない
2. ただしフロントから呼ばれていないため、ユーザー影響は出ていない
3. コスト計測が、使われていない Realtime だけを対象にしており、全ユーザーが通る Turn 経路を計測していない

「動かないコードが残っている」だけなら削除で済む。しかし Realtime は応答遅延と自然さで Turn 経路より優れており、模擬面接という製品の性質上、体験の質は事業価値に直結する。**したがってこれはコスト判断ではなく、製品判断である。**

## 3. 現状（すべて実測で確認済み）

### 3.1 実際に動作している経路

面接画面は Turn 経路のみを使用している。

| レイヤ | 実装 | モデル |
| --- | --- | --- |
| 音声認識 | `openai/transcribe_hints.go` `TranscribeWithHints` | `gpt-4o-mini-transcribe` |
| 音声認識(再送) | `openai/transcribe_hints.go` `TranscribeWithModel` | `gpt-4o-transcribe`（問題発話のみ） |
| 質問生成 | `openai/client_chat.go` `ChatInterview` | `gpt-4o-mini` |
| 音声合成 | `openai/tts.go` `TTS` | `tts-1` |

呼び出し元は `frontend/app/interview/hooks/useInterviewSession.ts:266, 553`。

### 3.2 動作していない経路

| 対象 | 状態 |
| --- | --- |
| `interview_realtime.go:169` 既定モデル `gpt-4o-realtime-preview` | 2026-05-07 停止済み。`GET /v1/models/...` が 404 |
| `openai/realtime.go:41` `POST /v1/realtime/sessions` | エンドポイント廃止。`Invalid URL` を返す |
| `frontend/lib/interview.ts:161` `createRealtimeToken` | 呼び出し元が存在しない |
| 本番の `OPENAI_REALTIME_MODEL` | 未設定。コード既定値がそのまま使われる |

### 3.3 コスト計測の状態

- `realtime_usage_logs` / `/admin/costs` は Realtime セッション専用
- Turn 経路のコストは記録されていない
- `realtime_usage_service.go:41-49` の単価既定値が旧価格のまま（音声入力 $100 / 出力 $200 → 現行 $32 / $64）
- 本番・ローカルとも `realtime_usage_logs` の完了レコードは 0 件

## 4. 対象範囲

### 対象

- AI面接の音声入出力の方式選定
- Realtime 実装（Backend / Frontend / 計測基盤）の存廃
- 面接1回あたりのコスト計測

### 対象外

- 面接の質問内容・深掘りロジック（`docs/design/interview-question-deepening.md` の管轄）
- 面接レポートの採点ロジック
- 履歴書レビュー・ES添削など他機能の AI コスト（Issue #1124 の管轄）

## 5. 判断軸

コストは判断軸として弱い。下表のとおり、いずれの案でも AWS 費用（月約2万円）と同程度かそれ以下に収まるためである。

**主たる判断軸は「模擬面接として成立する体験かどうか」とする。**

| 軸 | 説明 | 重み |
| --- | --- | --- |
| 応答遅延 | 学生が話し終えてから面接官が話し始めるまで。実面接の緊張感を再現できるか | 高 |
| 発話の自然さ | 抑揚・間。棒読みだと面接練習にならない | 高 |
| 割り込み対応 | 学生が話し始めたら面接官が黙るか（barge-in） | 中 |
| 運用コスト | 1面接あたりの API 費用 | 低 |
| 保守負荷 | 維持すべきコードと依存の量 | 中 |

## 6. 選択肢

### 6.1 比較

| | A. Turn に一本化 | B. Realtime へ移行 | C. 両方＋フラグ切替 |
| --- | --- | --- | --- |
| 応答遅延 | 2〜4秒（STT→LLM→TTS の直列） | 0.3〜0.8秒 | 選択次第 |
| 発話の自然さ | `tts-1` 相当。抑揚が乏しい | 会話音声として自然 | 選択次第 |
| 割り込み対応 | 不可 | 可（`interrupt_response`） | 選択次第 |
| 1面接あたり | 約 $0.06〜0.12 | 約 $0.18（`gpt-realtime-mini`） | — |
| 100人×毎日 | 約 $180〜360/月 | 約 $540/月 | — |
| 変更量 | 削除のみ | Backend API 移行＋Frontend 新規実装 | B に加えて分岐 |
| 保守負荷 | 最小 | 中 | 大 |

**費用の注記。** 「1面接あたり」の内訳（STT / LLM / TTS の比率）は本書に書かれていない。
確実に測れているのは STT 部分だけで、面接15分・学生発話7.5分として
`gpt-4o-mini-transcribe` が $0.023、`gpt-4o-transcribe` が $0.045
（`docs/research/interview-audio-eval/RESULTS_fallback.md`）。
**フォールバックの再送率が50%を超えると、mini + 再送は高精度モデル単独より高くなる。**

「100人×毎日」は上限想定である。この数字は学校向けの月額予算を大きく超えるため、
**実際の利用頻度を確認したうえで、超過しない上限（同時実行数か1人あたり回数）を
決める必要がある。** 現時点で上限の仕組みは無い。

### 6.2 各案の評価

**A. Turn に一本化**

死んだコードと未使用の計測基盤を削除し、現状の動作を正とする。最小構成であり、今日から正しい状態になる。

ただし応答遅延2〜4秒は、模擬面接としては明確に不自然である。実際の面接で面接官が毎回3秒黙ることはない。**この体験の質を許容できるかが唯一の争点。**

**B. Realtime へ移行**

現行API (`POST /v1/realtime/client_secrets`) と `gpt-realtime-mini` へ移行し、フロントに WebRTC 接続を実装する。

体験は大きく改善する。コスト増は月約 $390 で、AWS 費用と同オーダーに収まる。Backend 側は既に同時接続制御・月次アラート・トークン単位のコスト計算まで実装済みで、**移行に必要な足回りは揃っている**。未実装なのはフロントの接続処理のみ。

**C. 両方＋フラグ切替**

2つの音声経路を維持することになる。面接という単一機能に対して経路が2本あると、レポート生成・スコア反映・履歴表示のすべてが両対応を要求される。**得られるものに対して複雑さが見合わない。**

### 6.3 推奨

**B を推奨する。** ただし採用は「実際に話してみて質を確認してから」とする。

理由は、コスト差（月約 $390）が判断を左右する規模ではない一方、応答遅延の差（2〜4秒 → 0.3〜0.8秒）は模擬面接の価値そのものを左右するため。Backend 側の実装資産が既にあることも後押しになる。

`gpt-realtime-mini` は上位モデル `gpt-realtime` より安価だが発話品質は劣る。**mini で許容できるかは実際に聞いて判断する必要があり、本書では決めない。**

## 7. 要求事項

### 7.1 機能要求

| ID | 要求 | 対象案 |
| --- | --- | --- |
| F-1 | 面接開始時、選定した経路で音声対話を開始できる | A / B |
| F-2 | 面接の発話内容がテキストとして保存され、レポート採点に使える | A / B |
| F-3 | 面接1回ごとに、経路・所要時間・API費用が記録される | A / B |
| F-4 | 管理画面で日次・月次のコストを確認できる | A / B |
| F-5 | 同時接続数の上限を超える場合、面接開始を拒否する | B |
| F-6 | 学生が話し始めたら面接官の発話が停止する | B |

### 7.2 非機能要求

| ID | 要求 | 基準 |
| --- | --- | --- |
| N-1 | 応答遅延 | B 採用時、発話終了から応答開始まで 1.0 秒以内 |
| N-2 | セッション長 | 1回あたり 10 分を上限とする（既存 `INTERVIEW_SESSION_MINUTES`） |
| N-3 | コスト上限 | 月次閾値超過時に通知（既存 `REALTIME_MONTHLY_ALERT_THRESHOLD_USD`） |
| N-4 | 単価設定 | API 価格改定時にコード変更なしで追随できる（環境変数） |
| N-5 | 縮退 | 音声経路が利用不能な場合、ユーザーに理由が伝わるエラーを表示する |

### 7.3 コスト計測の要求

現在の最大の欠陥は「使われていない経路を計測し、使われている経路を計測していない」ことである。採用案に関わらず以下を満たす。

- 面接1回ごとに、STT / LLM / TTS それぞれの費用を記録する
- 単価はすべて環境変数で上書き可能とし、既定値は現行価格に一致させる
- 記録は既存の `/admin/costs` から参照できる

## 8. 受け入れ条件

1. Realtime の死んだコードが、削除または動作する状態のいずれかになっている
2. 面接を1回実施すると、その費用が管理画面で確認できる
3. 単価の既定値が、実施時点の OpenAI 公開価格と一致している
4. B 採用時: 応答遅延が N-1 を満たすことを実測で確認できている
5. 採用しなかった案について、判断理由が本書に記録されている

## 9. 決めきれていない点

| 項目 | 内容 | 判断者 |
| --- | --- | --- |
| 案の選択 | A / B のいずれか | プロダクト判断 |
| B 採用時のモデル | `gpt-realtime-mini` か `gpt-realtime`（約3倍） | 実際に聞いて判断 |
| STT モデル | `gpt-4o-mini-transcribe` を既定値として採用 | 単価は半額。**合成音声で検証済み**（`docs/research/interview-audio-eval/RESULTS_stt_hints.md`）で、CER・固有名詞正解率に差は出なかった。ただし **mini は「御社」を8/8で「本社」と誤認する**ため、この語を検知して高精度モデルへ再送するフォールバックを併用する。実発話の精度と再送率は未測定で、問題が出たら `OPENAI_WHISPER_MODEL=gpt-4o-transcribe` に戻す。**ただし本番・ステージングのタスク定義にこの環境変数が無く、戻す経路が未整備**（詳細は Design Doc） |
| 既存 Realtime 実装の扱い | A 採用時、削除するか凍結して残すか | 本書は削除を推奨 |

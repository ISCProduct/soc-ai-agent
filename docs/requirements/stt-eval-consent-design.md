# STT 評価用の実発話の収集：同意・撤回・削除窓口の設計（SOCAIAGENT-676）

音声認識（STT）を実発話で評価するための、収集ごとの同意・撤回・削除窓口・別バケット・アクセスログの設計。
**設計だけで、実装は後続課題（下の「後続課題」①〜⑤）に分ける。** 声は伏字にできないため、通常の面接データとは別に扱う。

方針の要点は [データプライバシー設計](../wiki/data-privacy.md) の「STT評価用に収集する発話音声」にあり、この文書はそれを実装できる形に落としたもの。
Notion の PRD・DesignDoc（SOCAIAGENT-676）と Figma（同意・撤回／削除依頼／`/privacy` の追記）は下書きで、文面・日付・件数・受付番号・営業日数はすべて仮案。

## 0. 既存の実発話の評価の扱い（U1）

STT モデルを `gpt-transcribe` に変えた根拠（2026-10-11）のうち、実際の面接音声での比較は再確認中のため、
確認が済むまで品質の根拠として扱わない。確認の経緯は Notion の DesignDoc（SOCAIAGENT-676）に置く。

## 1. 要件

### 1.1 ユーザーストーリー

- **学生として**、収集ごとに同意を自分で決め、いつでも撤回・削除したい。自分の声が知らないうちに使われないように。
- **開発者として**、同意のある実発話だけで誤変換を測りたい。Phase 2 の前に品質ゲート（意味が変わる誤変換が0件）を判定できるように。

### 1.2 受け入れ条件

| Given | When | Then |
|---|---|---|
| 同意していない学生 | 面接や評価を行う | 評価用の音声は1件も保存されない |
| 同意済みで音声が保存されている | 撤回する | 残っている音声がすべて削除され、撤回が履歴に残る |
| 保存から85日経った音声 | 日次ジョブが走る | 削除される（ジョブが止まっても、バケットの失効で保存から90日を超えない） |
| 教員・学校管理者・企業 | 評価用の音声を取得しようとする | 403 |
| 同意の文言を変えた（版を上げた） | 旧い版で同意した学生が録音しようとする | 受け付けない（新しい版への同意を求める） |
| 退会した学生 | 退会の処理が走る | 評価用の音声は退会の時点で削除する（12か月の保持の対象にしない） |
| 撤回と録音が同時に届いた | どちらが先に終わっても | 撤回のあとに音声がバケットに残らない（残っているのに削除済みにならない） |
| 18歳未満の学生（U7 の推奨のとき） | 同意の画面を開こうとする | 収集の対象にしない（画面を出さない） |

### 1.3 非機能要件

- 声は伏字にできない。**別保管・最小件数・最長保存（90日）・アクセスの記録**で守る。
- `user_id` を API のクエリやオブジェクトのキーに付けない（本人は認証から決め、キーはランダム）。
- 評価で外部の AI 事業者（OpenAI の音声認識。米国の事業者）へ音声を送ることを、同意の文言に明記する。外国にある第三者への提供として何を書くか（国名・その国の個人情報の制度・事業者の措置など）は U8 で決める。
- **評価以外に使わない。特に学習（ファインチューニング）のデータにしない。** 学習に使うなら、学習の同意（`training_consent_events`）とは別に、改めて同意を取る。同意の文言にも書く。
- 最初は**台本の読み上げだけ**を集める。自由発話は、病気や家庭のことなど要配慮個人情報が意図せず混ざりやすいので、入れるかどうかを U2 と一緒に決める。
- 課金している企業・学校を優遇する要素は無い（収集の対象・件数は条件の表だけで決める）。
- 収集の条件（方言・端末・環境）の偏りは、評価の結論に必ず注記する。

## 2. 全体の流れ

```
[学生] 同意の画面 ──(この回の収集への同意・版つき)──▶ stt_eval_consent_events（追記のみ）
   │                                                   └─▶ stt_eval_collection_sessions（件数・条件・期限）
   ├─ 録音（開いている回・今の版のときだけ受け付ける。撤回と同じ学生の行でロック）
   │      ├─▶ stt_eval_recordings に先に行を作る（uploaded_at は空。本文・声は DB に置かない）
   │      └─▶ 別バケット（非公開・暗号化・バージョニングなし・87日で失効）へ置いてから uploaded_at
   │
   ├─ 撤回 ──▶ 残っている音声をすべて削除（同期で試し、失敗分は日次ジョブが拾う）
   └─ 削除依頼（アプリ内フォーム／メール）──▶ stt_eval_deletion_requests（受付番号）
[音声R&D担当] 一覧（ページング）・試聴（認証つきの API から流す）──▶ stt_eval_access_logs
[評価の実行環境] 使い捨てのタスクで sttbench（手元に音声を保存しない）──▶ stt_eval_access_logs・バケットのアクセスログ
[日次ジョブ] 期限（85日）・撤回・退会・評価完了 の削除と再試行 ──▶ 削除に成功したときだけ deleted_at
```

## 3. データモデル（案）

スキーマは `Backend/migrations/` に up/down のペアで作る（GORM の AutoMigrate は使わない）。
日時は `training_consent_events` と同じく DB の時計（`NOW(3)`）で入れる。

### 3.1 `stt_eval_consent_events`（同意の履歴。追記のみ）

`training_consent_events`（#2168）に倣う。今の状態は「その学生の id が最大の行」で決める。

| 列 | 型 | 説明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `user_id` | BIGINT UNSIGNED | 学生本人 |
| `granted` | BOOL | 同意（true）／撤回（false） |
| `consent_text_version` | VARCHAR(32) | 操作したときに画面に出していた文言の版 |
| `created_at` | DATETIME(3) | `NOW(3)` |

- `granted = true` の行は、**1回の収集（3.2 の収集の回）への同意**として作る。「一度同意したら以後の録音すべてに使える」包括的な同意にはしない（「収集ごとに個別の同意」。data-privacy.md・`RESULTS_fallback.md`）。
- `granted = false`（撤回）は、その学生のすべての収集の回と、残っている音声すべてに効く。
- 学校経由の一括同意は作らない（U3）。

### 3.2 `stt_eval_collection_sessions`（収集の回。同意の範囲と期限）

学生が「この回の収集」に同意すると1行作る。録音はどれかの回にひも付け、回ごとに件数と期限を決める。
新しい回（追加の録音）には、そのたびに同意を取り直す。

| 列 | 型 | 説明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `user_id` | BIGINT UNSIGNED | 学生本人 |
| `consent_event_id` | BIGINT UNSIGNED | この回のための同意の行（3.1 の `granted = true`） |
| `max_recordings` | INT | この回で受け付ける録音の上限（同意の画面に出した件数。条件の表から決める） |
| `conditions` | VARCHAR(128) | この回で録る条件（例: `clean,noisy`。同意の画面に出す） |
| `expires_at` | DATETIME(3) | この回の受付の期限（例: 同意から24時間。過ぎたら録音を受け付けない） |
| `closed_at` | DATETIME(3) NULL | 上限に達した・期限切れ・撤回で閉じた日時 |
| `created_at` | DATETIME(3) | |

録音を受け付ける条件: 回が開いていて（期限内・上限未満・閉じていない）、その回の同意の行の `consent_text_version` が今の版と一致し、
その学生の最後の同意の行が撤回でないこと。

### 3.3 `stt_eval_recordings`（音声のメタデータ）

| 列 | 型 | 説明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `user_id` | BIGINT UNSIGNED | 本人（撤回・退会・依頼の削除で引く） |
| `session_id` | BIGINT UNSIGNED | 録音した収集の回（3.2）。その回の同意の行から、どの文言に基づくかを辿る |
| `object_key` | VARCHAR(128) | 別バケットのキー。`stt-eval/<ランダムな UUID>.webm`（`user_id` を入れない） |
| `script_id` | VARCHAR(64) NULL | 読み上げた台本の ID（版を含む。例: `2026-12-v1:017`）。manifest の `reference_text` は台本の一覧（版ごとに固定・PII を含まない）から復元する。最初は台本の読み上げだけなので必ず入る。自由発話を入れる（U2）なら NULL を許す |
| `condition` | VARCHAR(32) | 録音条件（`clean` / `noisy` / `reverb` / `quiet` / `fast` / `hesitation`。`sttbench.Case.Condition` と同じ語） |
| `device` | VARCHAR(32) | 端末の種類（PC内蔵マイク／スマホ など。機種名は持たない） |
| `duration_ms` / `size_bytes` | INT / BIGINT | 件数・容量の上限の判定に使う |
| `expires_at` | DATETIME(3) | 日次ジョブで消す期限（保存から85日。5章） |
| `uploaded_at` | DATETIME(3) NULL | バケットへ置き終えた日時。空のあいだは置いている途中か、置けなかった（4章の録音の受付の順番） |
| `delete_requested_at` | DATETIME(3) NULL | 削除が決まった日時（撤回・期限・依頼など）。これが入っていて `deleted_at` が空のものが、削除の再試行の対象 |
| `delete_reason` | VARCHAR(16) NULL | `expired` / `revoked` / `withdrawn` / `request` / `evaluated` |
| `deleted_at` | DATETIME(3) NULL | **バケットからの削除に成功した日時**。失敗したら入れない（音声が残っているのに削除済みに見せない）。`uploaded_at` が空の行は、アップロードの期限（5章）を過ぎてから消したときだけ入れる |
| `created_at` | DATETIME(3) | |

- 正解の文（読み上げた台本）は `script_id` だけを持ち、本文は台本の一覧から引く。自由発話の書き起こしは PII として**バケットの中にだけ**置き、DB・リポジトリ・ログに出さない。
- 「保存中」は `deleted_at IS NULL`（削除が決まって再試行中のものも含む）で数える。
- 削除しても行は残し（`deleted_at`）、「いつ・なぜ消したか」を説明できるようにする。退会のパージで行ごと消す。

### 3.4 `stt_eval_access_logs`（取得の記録）

| 列 | 型 | 説明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `actor_admin_user_id` | BIGINT UNSIGNED NULL | 操作した音声R&D担当（評価の実行環境なら NULL で `actor_job` を入れる） |
| `actor_job` | VARCHAR(64) NULL | 評価の実行（7章）の実行 ID |
| `action` | VARCHAR(16) | `list` / `stream` / `delete` / `eval_read` |
| `recording_id` | BIGINT UNSIGNED NULL | 一覧のときは NULL |
| `item_count` | INT | 一覧で返した件数 |
| `created_at` | DATETIME(3) | |

- 記録できなければ取得させない（記録が先・取得が後）。
- 声・書き起こしは持たない。保存期間は1年（案）。
- アプリを通らない読み取りも残すため、バケットのデータアクセスのログ（S3 のサーバーアクセスログ、または CloudTrail のデータイベント）を有効にし、読み取った主体（IAM ロール）とキーを1年残す。キーから `recording_id` を引けるので、この表と突き合わせられる。

### 3.5 `stt_eval_deletion_requests`（削除依頼の窓口）

| 列 | 型 | 説明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `receipt_no` | VARCHAR(16) | 受付番号（形式は仮案） |
| `user_id` | BIGINT UNSIGNED NULL | アプリ内フォームなら本人。メールで本人を確かめられないうちは NULL |
| `channel` | VARCHAR(8) | `form` / `email` |
| `status` | VARCHAR(16) | `received` / `done` / `no_audio` |
| `deleted_count` | INT | 消した件数 |
| `received_at` / `completed_at` | DATETIME(3) | 完了までの営業日数は仮案 |

## 4. API（案）

`Backend/api/openapi.yaml` に追記する。学生の API は同一オリジンの中継（`frontend/app/api/user/...`）を通す。

| 主体 | メソッド | パス | 内容 |
|---|---|---|---|
| 学生 | GET | `/api/user/stt-eval/consent` | 今の同意の状態・最後に変えた日時・今の文言の版・開いている収集の回 |
| 学生 | POST | `/api/user/stt-eval/sessions` | `{consent_text_version}`。この回の収集に同意し、収集の回（件数・条件・期限）を作る。版が今と違えば 409（古い画面からの同意を記録しない） |
| 学生 | POST | `/api/user/stt-eval/consent/revoke` | 撤回。開いている回を閉じ、同じ処理の中で残っている音声の削除を始める |
| 学生 | POST | `/api/user/stt-eval/sessions/:id/recordings` | 録音を1件受け付ける。回が開いていない・版が古い・上限を超えたら 403 / 409 / 429 |
| 学生 | GET | `/api/user/stt-eval/recordings/summary` | 保存中の件数と、いちばん早い削除予定日（音声そのものは返さない） |
| 学生 | POST | `/api/user/stt-eval/deletion-requests` | 削除依頼。受付番号を返す。音声が無ければ `no_audio` |
| 音声R&D担当 | GET | `/api/admin/stt-eval/recordings?condition=&device=&limit=&before_id=` | 一覧（`user_id` は返さない）。`id` の降順で、`limit` は既定 50・上限 200。続きは `next_before_id`（ほかの管理一覧と同じ形）。記録してから返す |
| 音声R&D担当 | GET | `/api/admin/stt-eval/recordings/:id/audio` | 音声を**認証つきの API からそのまま流す**（署名つき URL は出さない。URL の転送や、記録の無い複数回の取得をさせない）。記録してから流す |
| 音声R&D担当 | DELETE | `/api/admin/stt-eval/recordings/:id` | 評価が終わった音声を期限より前に消す（`evaluated`） |

- 管理側は**音声R&D担当の権限（新設・案）だけ**が使える。教員・学校管理者・企業ポータルは 403（存在の有無も推測させない）。
- **録音の受付・収集の回の作成・撤回は、どれも最初に同じ学生の `users` の行を `FOR UPDATE` でロックする**（同じ固定の行・同じ順序）。
  同意の行は追記なので、「最後の同意の行」をロックしても撤回の INSERT とは排他にならない。学生の行で揃えることで、撤回がコミットしたあとに
  録音が保存されることがない（撤回の処理は、ロックを取った時点で開いている回を閉じ、それ以前の録音をすべて削除の対象にする。
  録音の処理は、ロックを取ったあとで回が開いていることを確かめる）。相談機能（#2028）の質問作成と同じ考え方。
- 録音の受付は、**先に行を作り、置き終えたら印を付ける**順にする（撤回と入れ違っても音声だけが残らないように）。
  1. 音声のバイトを、ロックの外で一時領域に受ける
  2. ロックの中で回が開いていることを確かめ、`uploaded_at` が空の行を作ってコミットする
  3. ロックの外でバケットへ置く（置く処理には期限を付ける。案は5分）
  4. もう一度ロックを取り、行を読み直す。削除の対象になっていなければ `uploaded_at` を入れる。
     **削除の対象になっていれば（2 と 4 の間に撤回などが入った）、自分で音声を消して** `deleted_at` を入れる。置けなかったときも行を削除の対象にする
  - 撤回の処理が 2 と 4 の間に来ても、行があるので削除の対象になる。撤回側がバケットから消したあとに 3 が置いても、4 で読み直して消す
  - 4 の前に処理が落ちたときは、`uploaded_at` が空のまま残る。日次ジョブが拾って消す（5章）
  - 「先にバケットへ置いてからコミットする」順は採らない。コミットの前に落ちると、どの行からも辿れない音声がバケットに残る（87日の失効まで）

## 5. 削除

どのきっかけでも、まず `delete_requested_at` と `delete_reason` を入れ（削除の対象にする）、**バケットからの削除に成功したときだけ** `deleted_at` を入れる。
失敗したものは `delete_requested_at IS NOT NULL AND deleted_at IS NULL` で日次ジョブが再試行し、件数を監視する（3日続けて残れば通知）。

`uploaded_at` が空の行（置いている途中・置けなかった・落ちた）は、作ってから1時間（アップロードの期限の5分より十分長い）を過ぎたら日次ジョブが削除の対象にする。
S3 の削除はキーが無くても成功を返すので、**1時間を過ぎてから消したときだけ** `deleted_at` を入れる（それより前に消すと、あとから置かれた音声が残りうる）。

| きっかけ | 処理 | 漏れたとき |
|---|---|---|
| 期限 | 日次ジョブが `expires_at`（保存から85日）を過ぎた音声を削除の対象にして消す | バケットのライフサイクルで、保存から87日で失効させる（S3 の失効は非同期で1〜2日遅れうるので、遅れても90日を超えない） |
| 撤回 | API の中で対象にして消すのを試す | 日次ジョブが再試行する。「最後の同意が撤回の学生の、対象になっていない音声」も拾う |
| 退会 | 退会（論理削除）の時点で対象にして消す。12か月の保持の対象にしない | 日次ジョブが退会済みの学生の音声を拾う。パージで行も消す |
| 削除依頼 | フォームは本人の音声をすべて対象にして消し、`done`。メールは本人を確かめてから同じ処理 | 担当が受付番号で状況を追う |
| 評価が終わった | 音声R&D担当が消す（`evaluated`） | 期限で消える |

- バケットは**バージョニングを使わない**（消した音声の古い版を残さない）。サーバー側の暗号化・公開アクセスのブロックを必ず付ける。
- 削除が届く範囲を、バケットの外にも広げる（後続①④で確かめる）。
  - AWS Backup・レプリケーションの対象から、このバケットを外す（写しに削除が届かないため）
  - 評価のタスクの一時領域・ログ（CloudWatch など）・アプリのログに、音声・書き起こし・キーを出さない
  - メールの削除依頼は、メールアドレスと本文が受信箱に残る。受信箱のメールと `stt_eval_deletion_requests` の行の保存期間を決める（案: 完了から1年。10章）
- 評価の結果（7章）にある書き起こしも、録音と一緒に消す（結果は録音ごとのオブジェクトにし、同じ削除の処理で消す）。
- 削除の結果は件数と理由だけをログに出す（キー・本文は出さない）。

## 6. 画面（Figma の仮案）

- **収集への同意・撤回**（新規。PC・モバイル）: 未同意／保存中／エラー／同意済み／撤回の確認。面接画面の `ConsentDialog`（面接の録画の同意）とは**別枠**にし、面接の流れの中で同意を求めない。
- **削除依頼**（新規）: 入力／エラー／受付完了（受付番号）／音声なし。
- **`/privacy`**: 4章（保持期間）・5章（ユーザーの権利）・7章（お問い合わせ）に追記し、8章「音声認識の評価のための音声の収集」を新設する。
- 同意の文言に必ず入れること: 開発者が音声を聞くこと／保存期間（最長90日）／**評価で外部の AI 事業者（米国）へ音声を送ること**と、外国にある第三者への提供として必要な事項（U8。Figma に未反映）／**評価以外に使わず、学習のデータにしないこと**／いつでも撤回・削除を依頼できること／削除の窓口。
- 18歳未満の学生には同意の画面を出さない（U7 の推奨）。
- 文言を変えたら版を上げる（`TrainingConsentCard.tsx` の `TRAINING_CONSENT_TEXT_VERSION` と Go 側の定数を揃えるのと同じ運用）。

## 7. 評価（sttbench）への取り込み

**担当者の手元（ノート PC など）へ音声を保存しない。** 手元のコピーには5章の削除が届かず、「残っている音声をすべて削除」と「最長90日」を守れないため。

- 評価は、管理された実行環境（バケットを読めるロールを持つ使い捨てのタスク）で `sttbench` を動かす。音声はタスクの一時領域にだけ置き、
  タスクの終了で消える。タスクは1回の実行で終わり、音声を残さない。読み取りは 3.4 の記録（`eval_read`）とバケットのデータアクセスのログに残る。
- manifest はタスクの中で作る。`source: "real"`、`condition` は 3.3 と同じ語、`reference_text` は `script_id` から台本の一覧で復元する（`Backend/internal/sttbench/manifest.go`）。
  manifest にも音声にも `user_id` は入れず、`recording_id` だけを持つ。
- 結果は2つに分ける。
  - **集計**（件数・誤り率・意味が変わる誤変換の件数・条件ごとの内訳）: 個人を含まないので、評価の報告に載せてよい
  - **録音ごとの結果**（書き起こし・誤変換の箇所）: PII として同じバケットに `recording_id` ごとに置き、録音と一緒に消す（5章）。ターミナル・CI のログに出さない
- 担当者が音声を聞いて確かめるときは、管理画面から 4章の `/audio` で流す（保存させない）。
- 合成音声の結果と混ぜて比べない。条件の表のうち集まっていない条件は「未評価」と明記する。

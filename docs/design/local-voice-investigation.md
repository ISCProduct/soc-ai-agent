# DesignDoc: AI面接のローカル化 実機計測（調査結果）

- Issue: [#1209](https://github.com/ISCProduct/soc-ai-agent/issues/1209) (SOCAIAGENT-310)
- PRD: `docs/requirements/local-voice-investigation.md`
- 計測日: 2026-09-09
- 計測環境: Apple M3 Max / 36GB / GPU 30コア / macOS 26.6.2

## 0. 結論

### コスト目的なら、削るべきは音声であって LLM ではない

現行コストの内訳は STT 64% / TTS 31% / **LLM 6%**。
**LLM を安いモデルに替えても総額はほとんど動かない。**

### 完全ローカル化は 8GB で成立する（実測）

当初「8GBでは無理」と見えたが、モデル選定を変えたら成立した。

| | メモリ | 通し遅延 |
|---|---|---|
| whisper small + qwen2.5:3b + macOS say | **3.0GB** | **2.7秒** |
| （比較）現行クラウド | — | 2〜4秒 |

**API コストはゼロになり、遅延はむしろ速い。**
鍵は LLM の選定で、Qwen3 系（ハイブリッド推論）は英語の思考文が出力に混ざるため
使えず、推論型でない qwen2.5:3b が適していた（§3）。

### ただし本番にはそのまま持ち込めない

本番は ECS Fargate（x86・GPUなし）。本計測は Apple Silicon の GPU 前提であり、
**この数字は本番の見積もりに使えない**。適用先は展示会の現地マシン等に限られる（§7）。

### 推奨

| 目的 | 推奨 |
|---|---|
| **コスト削減が主目的** | STT と TTS だけローカル化。API費用の**95%**が消え、企業別カスタム質問・深掘り（`advanceQuestionPlan`）も維持できる |
| **機密性・オフライン動作が主目的** | 完全ローカル化。8GBで成立し遅延も改善するが、GPU付きの実行環境が要る |
| **end-to-end 音声マルチモーダル** | **非推奨。** 分割構成で既に現行同等の遅延が出ており、置き換えると深掘り機能が丸ごと失われる（§8） |

### この調査の最大の穴

STT 精度は**合成音声で測っており過大評価**。人間の発話で測り直すまで、精度の
数字を根拠に採否を決めるべきではない（§2, §9）。

## 1. 現行コストの内訳（実数）

単価は 2026-09-09 時点の公表値を取得（コード内定数は過去に10倍の乖離があったため不使用）。
gpt-4o-transcribe $0.006/分、gpt-4o-mini $0.15/$0.60 per 1M、tts-1 $15/1M文字。

| 想定 | STT | LLM | TTS | 合計/面接 |
|---|---|---|---|---|
| 10分・10ターン | $0.0300 | $0.0038 | $0.0198 | $0.0536 |
| **30分・15ターン** | **$0.0600 (64%)** | **$0.0055 (6%)** | **$0.0288 (31%)** | **$0.0943** |
| 30分・25ターン | $0.1000 | $0.0090 | $0.0468 | $0.1558 |

月1000面接で $94、5000面接で $472。

## 2. STT（whisper.cpp）実測

音声: 日本語39秒・211文字（学生の回答想定）。一致率は元原稿との文字単位一致。

| モデル | 処理時間 | 実時間比 | 一致率 | 実メモリ | ファイル |
|---|---|---|---|---|---|
| **small** | 1.53s | **25.5倍速** | 95.9% | **0.84GB** | 480MB |
| medium | 3.68s | 10.6倍速 | **97.0%** | 2.10GB | 1.4GB |
| large-v3-turbo | 2.49s | 15.6倍速 | 95.6% | 1.83GB | 1.5GB |

small の誤りは「データベースの設計→設定」「仕様の認識→使用の認識」の2箇所のみ。

**large-v3-turbo が medium より一致率で劣った**のは注目に値する。大きいほど良いとは限らない。

> ⚠️ **この一致率は過大評価。** 音声は `say` による合成音声で、人間の発話・
> 雑音・言い淀み・専門用語では確実に低下する。実運用の精度は実際の面接音声で
> 測り直す必要がある。

## 3. LLM（ollama）実測

現行の `interview_turn_prompt.go` のシステムプロンプトを再現し、会話履歴2往復＋
学生の回答を与えて次の質問を生成させた（プロンプト942トークン）。

| モデル | TTFT/応答 | 速度 | 実メモリ | 日本語品質 |
|---|---|---|---|---|
| qwen3:8b | TTFT 0.03s / 2.71s | 50 tok/s | 9.9GB (32kctx) | ✅ 4/4回とも整形済み |
| qwen3:4b | 2.50s | 81 tok/s | 3.2GB (4kctx) | ❌ **英語の思考文が本文に混入** |
| **qwen2.5:3b** | **0.23〜0.41s** | **105 tok/s** | **2.2GB (4kctx)** | ⭕ 4回中3回は自然。1回に軽微な破綻 |

8B の出力例（4回とも指示どおりの形式）:

```
ありがとうございます。次に、技術的な実績やスキルについてお聞かせください。
ありがとうございます。次に、今回の経験で得たスキルや成長点についてお聞かせください。
```

### qwen3:4b が使えない理由

`think: false` を指定しても、`/no_think` を付けても、**英語の推論文が `content` に
そのまま出る**。これは読み上げれば学生に聞こえてしまう。

```
Okay, let's see. The user is a student at a vocational school focusing on IT...
```

`think` 未指定だと推論は `thinking` 欄へ入るが `content` が空になる。
Qwen3 系のハイブリッド推論モデルは、この用途には**そのままでは使えない**。

### 推論型でない qwen2.5:3b は使える

同じ 8GB 級でも、推論型でない qwen2.5:3b は問題なく動いた。

```
それは非常に良い経験ですね。どのようにその取り組みを継続していきましたか？
それは素晴らしい経験ですね。このプロジェクトで何が具体的に成果を生んだと思いますか。
それは素晴らしい経験でした。具体的な結果や改善点について詳しく教えていただけますか？
```

深掘りの質問として自然で、8B の「ありがとうございます。次に〜」という定型より
むしろ会話らしい。ただし4回中1回、`その経験についての詳細が的印象的です` という
文法の破綻が出た。**軽微だが読み上げられる文なので、実運用では検出・再生成の
仕組みが要る**。

## 4. TTS（macOS `say`）実測

| 項目 | 値 |
|---|---|
| 日本語音声 | 9種類（Kyoko ほか） |
| 生成（短文・ウォーム） | 0.85s |
| 生成（39秒の音声） | 1.00s |
| 初回のみ | 3.20s（コールドスタート） |
| コスト | **0（OS内蔵）** |

品質は tts-1 に劣る。面接官の声として許容できるかは実際に聞いての判断が必要。

## 5. 通しの遅延（1ターン）

ウォーム状態で3回。STT → LLM → TTS を直列実行。

**whisper small + qwen3:8b**

| 回 | STT | LLM | TTS | 合計 |
|---|---|---|---|---|
| 1 | 1.52s | 0.77s | 0.89s | 3.18s |
| 2 | 1.42s | 0.36s | 0.84s | 2.62s |
| 3 | 1.47s | 0.47s | 0.86s | 2.79s |

**whisper small + qwen2.5:3b（8GB 構成）**

| 回 | STT | LLM | TTS | 合計 |
|---|---|---|---|---|
| 1 | 18.15s | 1.93s | 0.98s | 21.06s ← メモリ競合時（§6参照） |
| 2 | 1.46s | 0.41s | 0.87s | **2.74s** |
| 3 | 1.50s | 0.35s | 0.86s | **2.71s** |

**平均 2.7〜2.9秒。現行クラウド経路（2〜4秒）と同等かやや速い。**
内訳では STT が約半分を占める。

## 6. 8GB 環境（#792 の制約）で成立するか

| 構成 | メモリ | 通し遅延 | 判定 |
|---|---|---|---|
| whisper small + qwen3:8b(32kctx) | 0.84 + 9.9 = 10.7GB | 2.86s | ❌ 収まらない |
| whisper small + qwen3:4b(4kctx) | 0.84 + 3.2 = 4.0GB | — | ❌ 品質が使えない（§3） |
| **whisper small + qwen2.5:3b(4kctx)** | 0.84 + 2.2 = **3.0GB** | **2.7s** | ⭕ **成立する** |
| whisper small のみ（LLMはクラウド） | 0.84GB | — | ⭕ 余裕で収まる |

**8GB での完全ローカル化は成立する。** whisper small + qwen2.5:3b で 3.0GB、
通し 2.7秒。現行クラウド（2〜4秒）より速い。

### メモリ競合で STT が12倍遅くなる

8B と 3B を同時に常駐させた状態で通しを測ると、**STT が 1.5秒 → 18.15秒**に
悪化した（同条件の次の2回は 1.46s / 1.50s）。

複数モデルを載せるとメモリ競合で音声処理が破綻する。運用では
**常駐モデルを1つに絞る**か、明示的にアンロードする制御が要る。

## 7. 本番への適用可能性

本番は ECS Fargate（x86・GPUなし）。本計測は Apple Silicon の GPU（Metal）前提で、
**同じ速度は出ない**。CPU のみの実行は未計測だが、桁で遅くなる想定。

適用先の候補:

| 適用先 | 可否 | 備考 |
|---|---|---|
| 展示会の現地マシン | ⭕ | 本番は展示会時のみ起動する運用（#1214 の `/prod`）と相性が良い |
| GPU付きインスタンス | △ | 常時起動なら固定費が API 費用を上回りうる。要試算 |
| 現行の Fargate | ❌ | GPU が無い |

## 8. 音声マルチモーダル（speech-to-speech）

Qwen3-Omni は日本語を音声入出力ともサポートし、低遅延を狙った構成を持つ。
Apple Silicon では mlx-audio / MLX 系が有力。

ただし**採用は推奨しない**。理由は2つ。

1. **遅延の実利が薄い。** 本計測で分割構成が既に 2.86秒（現行と同等）を出している
2. **機能退行が大きい。** `advanceQuestionPlan` は Turn ハンドラ内でしか呼ばれず、
   speech-to-speech に置き換えると企業別カスタム質問と深掘りが丸ごと失われる
   （`docs/design/interview-question-deepening.md` の成果物）

## 9. 未検証・次に測るべきこと

- **実際の人間の音声での STT 精度**（本調査の最大の穴。合成音声では過大評価になる）
- qwen2.5:3b の日本語破綻（4回中1回）の発生率と、検出・再生成の仕組み
- CPU のみ（Fargate 相当）での実行速度
- `say` の音声品質の主観評価（面接官の声として許容できるか）
- GPU付きインスタンスの固定費 vs API 従量課金の損益分岐点

## 10. 再現手順

```bash
brew install whisper-cpp ollama
ollama serve &
ollama pull qwen3:8b
curl -L -o ggml-small.bin \
  https://huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-small.bin

# 日本語テスト音声の生成
say -v Kyoko -o ans.aiff -f ans.txt
ffmpeg -i ans.aiff -ar 16000 -ac 1 ans.wav

# STT
whisper-cli -m ggml-small.bin -f ans.wav -l ja -np -nt -t 10
```

# 劣化音声での音声認識の実測（#1603 第1段階）

- 実行日: 2026-09-29
- データ: `manifest_degraded.jsonl`（8基準ケース × 28条件 = 224件、すべて合成音声）
- 生成: `python3 make_degraded.py`
- ツール: `Backend/cmd/sttbench`

## なぜ測ったか

利用者からの要望は「**クライアントの環境によって音声の状態が悪いことがあるので、その悪いデータでも誤変換がかからない状態にしてほしい**」だった。

ところが既存フィクスチャは**8ケースすべてがクリーンな合成音声**で、`condition` フィールドは全件未設定だった。#1484 で録音条件別の集計機能は入れたのに、**集計する対象のデータが1件も無かった**。

## 生成した条件

| condition | 想定する実環境 | 強度 |
|---|---|---|
| `noisy-{white,pink}-snr{20,10,5,0}` | 自宅・カフェ・家族の生活音 | SNR 20 / 10 / 5 / 0 dB |
| `reverb-{weak,mid,strong}` | 硬い壁の部屋・反響 | 3段階 |
| `quiet-{12,24,36}db` | マイクが遠い・小声 | -12 / -24 / -36 dB |
| `clipped-{light,heavy}` | マイク入力が過大で歪む | 2段階 |
| `lowband-{phone,narrow}` | 安価なヘッドセット・電話品質 | 300-3400Hz / さらに狭い |
| `lowbitrate-{24k,12k,6k}` | 回線が細くコーデックが潰れる | 3段階 |
| `dropout-{3s,15s,08s}` | 通信の瞬断・パケットロス | 間隔3段階 |
| `fast-{1.3x,1.6x}` | 早口 | 2段階 |
| `combo-noisy10-lowband` | 雑音のある環境 + 安価なヘッドセット | 組み合わせ |

**SNR は狙った値ではなく実測で合わせている。** 「音声のRMSを測る → 目標SNRになる雑音ゲインを計算する → 生成後にもう一度測って確認する」の3段で、`audio/degraded_levels.tsv` に `target_snr_db` と `achieved_snr_db` の両方を記録する。72件すべてで**誤差 0.000 dB**。

雑音は seed 固定なので、同じ入力からは毎回同じ音声ができる。

## 測り方でつまずいた点（先に書く）

最初、「正解と違うケース」を数えて「高精度48件 / mini 53件が壊れている」と集計した。**これは誤りだった。**

`clean`（無劣化）でも不一致が出る。`30パーセント` → `30%` のような表記ゆれで、`RESULTS_synthetic.md` が既に「意味は保たれる」と記録しているものである。これを「劣化で壊れた」に数えていた。

**各ケースを自分の clean 結果と比較する**ように直したところ、結論が変わった。

| モデル | 劣化で悪化 | うち固有名詞を落とした |
|---|---|---|
| `gpt-4o-mini-transcribe` | **17 / 216** | 3 |
| `gpt-4o-transcribe` | **20 / 216** | 7 |

`RESULTS_synthetic.md` の「指標の作り方次第で誤った結論になり得た」がここでも起きた。**基準を持たない比較をしないこと。**

## 1. 集計指標では何も見えない

| モデル | 平均CER | 意味CER | 固有名詞 | 数値 | 失敗率 |
|---|---|---|---|---|---|
| `gpt-4o-transcribe` | 0.020 | 0.004 | 90.6% | 100.0% | 0.4% |
| `gpt-4o-mini-transcribe` | 0.021 | 0.005 | 92.3% | 100.0% | 0.4% |

**CER 0.020 と 0.021 の差で判断すると「両モデルとも劣化に強い」と結論してしまう。** 固有名詞1語の破壊は CER にほとんど現れない。面接では固有名詞（企業名・技術名）と数値（実績）が最も重要なので、**この用途に CER は向いていない。**

**`Go` は SNR20（ほぼ聞こえる程度の雑音）や電話品質のヘッドセットで既に壊れる。** 2文字の英単語で同音の候補が多いためと考えられる。

```

認識  バックエンドエンジニアとして、事業者の課題を解決したいです。    ← 高精度
認識  バックエンドエンジニアとして、貴社者の課題を解決したいです。    ← mini

正解  はい、あります。質問をお願いします。
```

## 3. 高精度モデルへの切り替えでは直らない

劣化で悪化したのは **mini 17件 / 高精度 20件**で、固有名詞の脱落は **mini 3件 / 高精度 7件**。高精度モデルのほうがむしろ多い。

壊れ方の質も違う。mini は `Goat` のような**誤った語に置き換える**のに対し、高精度モデルは `Go` を**丸ごと落とす**ことがある。どちらも面接の評価には悪い。

**#1603 の②「再送率を測って既定モデルを決める」は、この結果を前提に見直す必要がある。** 「高精度にすれば劣化に強い」という想定は成り立たない。

## 4. 補助語（STT hints）は劣化音声でも効く

固有名詞ケースに絞った56件（2ケース × 28条件）で、補助語あり/なしを比較した。

補助語: `御社, 株式会社サンプルソフト, サンプルソフト, バックエンドエンジニア, AWS, Docker, Go, MySQL, SaaS, TypeScript`

| モデル | 補助語なし | 補助語あり |
|---|---|---|
| `gpt-4o-mini-transcribe` | 12/54 悪化・固有名詞 96.9% | **5/54 悪化・固有名詞 99.5%** |
| `gpt-4o-transcribe` | 11/54 悪化・固有名詞 96.4% | **3/54 悪化・固有名詞 100.0%** |

```
ピンク雑音SNR0 (mini)   なし: ボートAWSを使って、ドクター上で動く...
                        あり: GoとAWSを使って、Docker上で動く...
ピンク雑音SNR5 (mini)   なし: WordとAWSを使って、ドクター上で動く...
                        あり: GoとAWSを使って、Docker上で動く...
雑音SNR5 (高精度)       なし: Bot AWSを使って...
                        あり: GoとAWSを使って...
電話帯域 (mini)         なし: GoatAWSを使って...
                        あり: GoとAWSを使って...
小声-36dB (mini)        なし: Goat AWSを使って...
                        あり: GoとAWSを使って...
```

**SNR 0 という最悪条件でも補助語だけで復元できる。** これは `BuildSTTHints` として既に実装済みの機能である。

残った未解決は `noisy-white-snr0` の mini で、`Docker` は復元されるが `Go` は落ちたままだった。

## 5. 現行のフォールバックは今回の誤変換を1件も拾わない

`stt_fallback.go` の5条件を実測結果に当てると、すべて `FallbackNone` になる。

| 条件 | `Goat AWS` | `ドクター上で動く` | `利用者` → `御社` |
|---|---|---|---|
| `stt_error` / `empty_result` / `unintelligible` | 該当せず | 該当せず | 該当せず |
| `too_short_for_duration` | 文字数は十分 | 十分 | 十分 |
| `role_confusion`（`本社` を検出） | 該当せず | 該当せず | **`御社` なので検出せず** |

しかも仮に発動しても、再送先の高精度モデルが同じケースで壊れるので直らない（§3）。

**現行のフォールバックは「結果が無い」ケース専用で、「一見成功しているが内容が誤っている」ケースには無力である。**

## この結果で判断してはいけないこと

**劣化させたのは合成音声であり、実発話の代わりにはならない。**

- ffmpeg で付加した雑音は、実際の生活音（人の話し声・食器・車）とは統計的性質が違う
- 合成音声の発音は人間と違い、個人差・訛り・声量の揺れを含まない
- `reference_text` が固定なので、言い直し・言い淀みの実際の分布を反映しない
- 8基準ケース・固有名詞13語という母数の小ささは `RESULTS_synthetic.md` から変わっていない
- **端末差（ノートPC / スマートフォン / 外付けマイク）は再現していない。** ffmpeg の劣化はあくまでモデルであって、実際の端末が作る歪みではない

言えるのは「**ここで模した劣化の範囲では、補助語が固有名詞の破壊を大きく減らす**」までである。

## 再現手順

```sh
# 劣化音声を生成する（元の8ケースの音声が audio/ にある前提）
python3 make_degraded.py

# 補助語なし
go run ./cmd/sttbench -manifest ../docs/research/interview-audio-eval/manifest_degraded.jsonl \
  -format wav -out <リポジトリ外>

# 補助語あり
go run ./cmd/sttbench -manifest ../docs/research/interview-audio-eval/manifest_degraded.jsonl \
  -format wav -hints '会社名|読み|職種|企業情報' -out <リポジトリ外>
```

**元になる8ケースの音声はリポジトリに追跡されていない**（`docs/research/**` が無視され `RESULTS_*.md` だけ例外）。#1484 以前からの状態で、手元に無い場合は先にそちらを用意する必要がある。生成器とマニフェストだけでは再現できない。

## 次にやること

- **補助語の語の出どころを増やす。** 現状は企業ブリーフの技術スタックからの正規表現抽出だけ。`companies.TechStack` が空の企業では保護が効かない。求人票・学生の履歴書の固有名詞を足す（#1603 の③）
- **入力側の `autoGainControl`。** `MEDIA_CONSTRAINTS` に `echoCancellation` と `noiseSuppression` は入っているが `autoGainControl` が無い。小声 -24dB / -36dB で壊れているので効く可能性がある
- **フォールバック条件の見直し。** 「結果が無い」専用になっている（§5）
- WEBM 形式での測定（本番が送る形式。本測定は WAV のみ）
- 実発話での確認（#1603 の⑤）

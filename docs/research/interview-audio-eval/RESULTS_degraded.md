# 劣化音声での音声認識の実測（#1603 第1段階）

- 実行日: 2026-09-29
- データ: `manifest_degraded.jsonl`（8基準ケース × 28条件 = 224件、すべて合成音声）
- 生成: `python3 make_degraded.py`（**この run の後に信号レベルの測り方を直した。下記【撤回】**）
- 集計: `python3 compare_degraded.py`（**この run の時点では未追跡。下記「集計コード」**）
- ツール: `Backend/cmd/sttbench`

> **この記録は修正前の生成器・修正前の集計実装によるものである。** SNR ラベルと失敗率・CER の読み方に下記の留保が付く。OpenAI API の残高切れ（`429 insufficient_quota`）で再測定できていない。

## なぜ測ったか

利用者からの要望は「**クライアントの環境によって音声の状態が悪いことがあるので、その悪いデータでも誤変換がかからない状態にしてほしい**」だった。

ところが既存フィクスチャは**8ケースすべてがクリーンな合成音声**で、`condition` フィールドは全件未設定だった。#1484 で録音条件別の集計機能は入れたのに、**集計する対象のデータが1件も無かった**。

## 生成した条件

| condition | 想定する実環境 | 強度 |
|---|---|---|
| `noisy-{white,pink}-snr{20,10,5,0}` | 自宅・カフェ・家族の生活音 | SNR 20 / 10 / 5 / 0 dB |
| `reverb-{weak,mid,strong}` | 硬い壁の部屋・反響 | 3段階 |
| `quiet-{12,24,36}db` | マイクが遠い・小声 | -12 / -24 / -36 dB |
| `clipped-{light,heavy}` | マイク入力が過大で歪む | 2段階 |
| `lowband-{phone,narrow}` | 安価なヘッドセット・電話品質 | 300-3400Hz / さらに狭い |
| `lowbitrate-{24k,12k,6k}` | 回線が細くコーデックが潰れる | 3段階 |
| `dropout-{3s,15s,08s}` | 通信の瞬断・パケットロス | **120msの無音を挿入する間隔**が 3秒 / 1.5秒 / 0.8秒。ID は小数点を抜いた表記なので `15s` は15秒ではなく1.5秒 |
| `fast-{1.3x,1.6x}` | 早口 | 2段階 |

雑音は seed 固定なので、同じ入力からは毎回同じ音声ができる。

### 【撤回】「SNR は実測で合わせている / 誤差 0.000 dB」

初版はここに「**SNR は狙った値ではなく実測で合わせている**」「`target_snr_db` と `achieved_snr_db` を両方記録し、72件すべてで**誤差 0.000 dB**」と書いていた。**これは撤回する。**

`achieved_snr_db` は測定ではなく恒等式だった。

```
gain       = (src_mean - target_snr) - n0
noise_mean = n0 + gain                     ← volume は厳密な線形ゲイン
achieved   = src_mean - noise_mean = target_snr   ← 常に一致
```

確かめていたのは「`volume` フィルタが指示どおりのゲインを掛けたか」だけで、疑う余地のなかったことである。**「72件すべて誤差 0.000 dB」は品質の証拠ではない。**

実害が2つある。

1. **信号レベルに無音込みのファイル全体RMSを使っていた。** 音声フィクスチャは前後と語間に無音を含むため、`src_mean` は発話中のレベルを過小評価する。レビューで別の信号を使って実走した結果では、無音込み10秒（発話4秒）のファイルで `mean_volume` が **-37.1 dBFS**、発話区間だけだと **-33.1 dBFS** で、**ラベルより実際は 4.0 dB 楽な条件**になっていた（`target 20dB` → 実際 24dB、`0dB` → 実際 4dB）。無音率はケースごとに違うので、**8ケース間でもラベルが揃っていない。**
2. **混合後のファイルで測っていない。** `combo-noisy10-lowband` は `amix` の後に 300-3400Hz のバンドパスを掛けるので、配信されるファイルの SNR は 10dB ではない。

したがって、**この記録の `noisy-*` / `combo-*` の SNR ラベルは発話区間基準ではなく、実際はラベルより楽な条件である。** 後述の「SNR 0 という最悪条件でも補助語だけで復元できる」（§4）も、実際にはもっと楽な条件での結果として読むこと。

生成器は修正済み（`silenceremove` で無音を落としてから信号レベルを測る / `achieved_snr_db` は廃止して `src_speech_mean_db` と `noise_mean_db` を生で残す / `pre` と `snr_db` の併用はガードで弾く）。ただし**この記録の数値は修正前の音声によるもので、再測定はしていない**（OpenAI API の残高切れ・`429 insufficient_quota`）。修正後の音声で測り直すと SNR ラベルが実質的に厳しくなるため、**条件ごとの数値は次の run で置き換える必要がある。**

## 測り方でつまずいた点（先に書く）

最初、「正解と違うケース」を数えて「高精度48件 / mini 53件が壊れている」と集計した。**これは誤りだった。**

`clean`（無劣化）でも不一致が出る。`30パーセント` → `30%` のような表記ゆれで、`RESULTS_synthetic.md` が既に「意味は保たれる」と記録しているものである。これを「劣化で壊れた」に数えていた。

| `gpt-4o-mini-transcribe` | **17 / 216** | 3 |
| `gpt-4o-transcribe` | **20 / 216** | 7 |

分母の 216 は `224 - 8`。`clean` の8件は**比較の基準そのもの**なので「劣化で悪化」の分母から外れる（自分自身と比べることになる）。

`RESULTS_synthetic.md` の「指標の作り方次第で誤った結論になり得た」がここでも起きた。**基準を持たない比較をしないこと。**

### 集計コードは `compare_degraded.py`

**この表の数値は、スクリプトが無かった時点の手元のアドホックな処理で数えたものである。** 結論を一度ひっくり返した処理がリポジトリに無く、音声を揃えた人でも再計算できない状態だった。

## 3. 高精度モデルへの切り替えでは直らない

劣化で悪化したのは **mini 17件 / 高精度 20件**で、固有名詞の脱落は **mini 3件 / 高精度 7件**。高精度モデルのほうがむしろ多い。

## この結果で判断してはいけないこと

**劣化させたのは合成音声であり、実発話の代わりにはならない。**

- ffmpeg で付加した雑音は、実際の生活音（人の話し声・食器・車）とは統計的性質が違う
- 合成音声の発音は人間と違い、個人差・訛り・声量の揺れを含まない
- `reference_text` が固定なので、言い直し・言い淀みの実際の分布を反映しない
- 8基準ケース・固有名詞13語という母数の小ささは `RESULTS_synthetic.md` から変わっていない
- **端末差（ノートPC / スマートフォン / 外付けマイク）は再現していない。** ffmpeg の劣化はあくまでモデルであって、実際の端末が作る歪みではない

測り方そのものにも、この記録の時点で分かっている穴がある。

- **SNR ラベルは発話区間基準ではない。** 無音込みのファイル全体RMSから雑音ゲインを決めていたので、`noisy-*` / `combo-*` は**ラベルより実際は楽な条件**である。無音率はケースごとに違うのでケース間でもラベルが揃っていない。`combo-noisy10-lowband` は混合後にバンドパスが掛かるので配信ファイルの SNR は 10dB でもない（冒頭の【撤回】）。初版はこれを「実測で合わせている」と**強みとして**書いていた
- **APIエラーが混ざると CER が良く出る。** 測定時の実装は `MeanCER` の分母に失敗ケースを残していた。**残高切れの今、次に実行する人がまさに踏む。** 現在はAPIエラーだけを分母から外し、`errored_cases` を分けて出し、4xx が3件続いたら打ち切るようにしてある。それでも**`mean_cer` を読むときは必ず `errored_cases` を一緒に見ること**
- **【撤回】この記録の固有名詞正解率・平均CERは、認識失敗（空・短すぎる出力）を母数から外した値である。** 一時期、APIエラーと同じ扱いで `r.Failed` を平均から除外していた。APIエラーと違って認識失敗は**モデルの測定結果そのもの**なので、外すと「何も返さないほど成績が良く見える」逆転が起きる（完璧1件＋無音1件で平均CER 0.000 / 固有名詞 100% になっていた）。
  現在は認識失敗を**全ミスとして数える**ように直した。したがって下記の数値は**次回実行時に悪化する方向でずれる**。
  - §3 の「固有名詞 90.6% / 92.3%」「平均CER 0.020 / 0.021」
  - §4 の「固有名詞 96.9% / 99.5% / 96.4% / 100.0%」
  再測定していないので、ここに書いてある値は上振れしたものとして読むこと。悪化の件数（`12/54` 等）は clean との突き合わせなので影響を受けない
- **補助語の効果に対照がない。** 「補助語あり」と比べているのは「prompt 自体が無い群」であって、固有名詞を教えた効果と prompt フィールドの存在そのものの効果が分離できていない（§4）
- **「劣化で悪化」の分母 216 は `clean` の8件を除いた数。** `clean` は比較の基準そのものなので入らない。全体指標（§1）の母数 224 とは別物で、同じ表の中で混ぜて読まないこと

言えるのは「**ここで模した劣化の範囲では、prompt に補助語を載せた群のほうが固有名詞の破壊が少なかった**」までである。「補助語の語が効いた」はデコイ群を測るまで言えない。

## 次にやること

- **修正後の生成器で測り直す（最優先）。** 信号レベルを発話区間基準にしたので SNR ラベルが実質的に厳しくなる。条件ごとの数値は次の run で置き換える。残高の回復が前提
- **デコイ群を1本足す。** 補助語と同じ長さで無関係な語を並べた prompt を測る。これが無いと「補助語の語が効いた」のか「prompt フィールドがあると出力が整う」のかが分けられない（§4）

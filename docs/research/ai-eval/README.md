# AI出力品質の評価ハーネス（#1525）

ES添削・履歴書レビュー・面接レポートの出力品質を、固定のゴールデンセットで測る。

**このハーネスの目的は「誰が測っても同じ数字が出ること」**。プロンプト・モデル・
パラメータを変えたときに良くなったのか悪くなったのかを、実行者に依らず判定できる
ようにする。単発の実験スクリプトではなく、入力（このディレクトリの jsonl）・
手順（`Backend/cmd/aibench`）・出力（結果JSON）を固定し、前回結果との差分を取れる形にしてある。

音声認識の `Backend/cmd/sttbench` と `docs/research/interview-audio-eval/` が先例。
同じ形の手動バッチとして運用する。

---

## 使い方

```bash
cd Backend

# 動作確認（各ラベル1件ずつ = 3件、APIは呼ばない）
go run ./cmd/aibench -target resume -manifest ../docs/research/ai-eval/resume.jsonl -limit 1 -dry-run

# 本番（同一入力3回でばらつきも測る）。結果はリポジトリ外へ
go run ./cmd/aibench -target resume -manifest ../docs/research/ai-eval/resume.jsonl -n 3 -out /tmp/resume-$(date +%Y%m%d).json

# モデルを変えて比較
go run ./cmd/aibench -target resume -manifest ../docs/research/ai-eval/resume.jsonl -model gpt-4o -out /tmp/resume-4o.json

# 前回との差分（劣化があれば終了コード1）
go run ./cmd/aibench -diff /tmp/resume-prev.json,/tmp/resume-4o.json
```

主なフラグ:

| フラグ | 意味 |
|---|---|
| `-target` | `es` / `resume` / `interview-report` |
| `-manifest` | ゴールデンセットの jsonl |
| `-n` | 同一入力の実行回数（再現性の測定用。2以上で意味を持つ） |
| `-model` | モデル名。未指定なら本番と同じ既定値 |
| `-limit` | **各ラベルから**先頭N件だけ実行（動作確認用） |
| `-yes` | 概算コストの確認を省略 |
| `-dry-run` | APIを呼ばず、マニフェスト検証と概算コストだけ出す |
| `-out` | 結果JSONの出力先（**リポジトリ外**を指定すること） |

終了コード: `0` 正常 / `1` エラーまたは劣化検知 / `2` 引数不正 /
`3` APIキー未設定 / `4` 設定の問題で実行中止 / `130` 確認で中止。

### 安全弁

- **CIでは実行しない**。課金と実行時間のため、手動バッチとして運用する。
- 実行前に「件数 × 回数」から概算コストを表示し、`-yes` が無ければ確認を求める。
- 結果には必ず**モデル名・実行日時・マニフェストのSHA256**を残す。
  OpenAI 側のモデル更新で同じモデル名でも数字が変わるため、
  いつ・どのモデルで・どの入力で測ったかが無い結果は比較に使えない。
- 結果JSONには LLM の出力本文が入る。リポジトリ外へ置くこと（ターミナルには本文を出さない）。

## 前提: RAGサービスの起動が必要か

| target | RAGの起動 | 理由 |
|---|---|---|
| `es` | **必要** | プロンプトが Python 側（`rag/services/es_review.py`）にあるため、HTTP で `/es/review` を叩く以外に本番と同じものを測る方法がない |
| `resume` | 不要 | Go のプロンプト生成関数を呼び、OpenAI を直接叩く |
| `interview-report` | 不要 | 同上 |

**ES添削は RAG を起動せずには評価できない。**

```bash
make rag-up     # または docker compose up -d --build chroma rag-review
export RAG_REVIEW_URL=http://localhost:9000
export RAG_INTERNAL_TOKEN=...   # RAG側と同じ値。未設定だと 401 で即中止する
go run ./cmd/aibench -target es -manifest ../docs/research/ai-eval/es.jsonl -n 3 -out /tmp/es.json
```

モデル名は RAG コンテナの `OPENAI_CHAT_MODEL` で決まるため、ハーネスは `/health` の
`chat_model` から実際の値を読む。`/health` に `chat_model` が無い（RAGのイメージが古い）
場合はエラーになるので、`make rag-up` でリビルドするか `-model` で明示する。
推測でモデル名を埋めると結果に残るモデル名が嘘になるため、自動では埋めない。

## 測る指標

| 指標 | 定義 | 読み方 |
|---|---|---|
| 破損率 | (JSON不正 ＋ 出力上限到達 ＋ 使えない出力) / 計測できた実行回数 | 低いほど良い |
| 再現性 | 同一入力n回の正規化スコアの**母**標準偏差（ケードごと、その平均と最大） | 小さいほど良い。0.1超のケースは `unstable_case_ids` に出る |
| 弁別力 | ゴールドラベル（良/中/悪）と平均スコアの**順位相関** | 1.0が完全一致 |
| 指示遵守率 | 違反が1件も無かった実行の割合（破損した実行は分母から外す） | 高いほど良い |
| レイテンシ | p50 / p95（最近傍順位法。補間しない） | — |
| コスト | 1件あたり／合計の概算。単価は `internal/services/costs` の表を再利用 | — |

### 弁別力に順位相関を使う理由

モデルごとにスコアの中心がずれる。「良は7点以上」のような**絶対値の一致は要求しない**。
中心が1点下がっただけのモデルを不合格にしてしまうため。見たいのは
「良・中・悪の順に並ぶか」だけ。

ゴールドラベルは3値で同順位が大量に出るので、単純な差の2乗の式は使えない。
順位に変換してからピアソン相関を取っている（同順位は平均順位）。

注意: スコアが「順序は正しいが全て異なる」場合、ラベル側の同順位に押し下げられて
1.0 には届かない（good/mid/bad を10件ずつにした本ゴールデンセットの構成では 0.943）。
スコア側の同順位がラベル側と一致したときだけ 1.0 になる。
**実行間の比較に使い、1.0 との差を絶対視しないこと。**

### 破損率に混ぜないもの

- **通信エラー・レート制限（429）・API側の5xx** は `network_error` として別に数え、
  破損率とレイテンシの両方から除外する（`計測できず N回` として表示）。
  実測でこれを混ぜると数字が壊れた: ローカルの通信断2回で破損率が11.1%になり、
  120秒のタイムアウトが p95 を120,001msに押し上げた。どちらもモデルの品質とは
  無関係で、測り直せば消える。
### 履歴書レビューのスコアと「やり直し前」の数字

総合スコア（0〜100）は LLM に出させず、項目スコア5つ（specificity / achievement /
role_fit / completeness / readability、各0〜5）の加重和から本番と同じ
`resume.ComputeResumeOverallScore` で算出する（#1529）。重みは候補者区分で変わる。

本番はルーブリック違反のとき別プロンプトで1度やり直してからスコアを捨てる。
ハーネスはリトライを通さないので、**`schema_incomplete` の発生率はやり直し前の値**である。
ユーザーが実際にスコア無しになる割合はこれより低い。

- **認証エラー（401/403）・モデル名の誤り（404）・APIキー未設定** は設定の問題なので、
  検知したら即座に実行を打ち切る（終了コード4）。続行すると「破損率100%」という
  もっともらしい数字が出て、設定ミスを品質の問題と読み違える。

### 本番のリトライを通していないこと

ハーネスは本番のクライアント（`internal/openai`）を通さず、生のHTTPで1回だけ叩く。

- 本番クライアントは最大5回リトライし、温度やモデルまでフォールバックする。
  それを通すと破損率は「リトライ後の値」になり、プロンプト変更の効果が消える。
- `usage`（実トークン数）と `finish_reason` が本番クライアントの戻り値に無い。
  コストと「出力上限到達」はこの2つが無いと測れない。

したがって**ここで出る破損率はモデル素の値**で、ユーザーが体験する失敗率
（リトライ後）とは別物。ユーザー体験としての失敗率を知りたいときは本番のログを見ること。

ただし JSON の**復旧**（前後の散文やコードフェンスを落として最外の `{...}` を取り出す）は
本番と同じように通してから判定する。通さないと、本番では読めている出力まで破損として
数えてしまう。復旧が必要だったことは `json_not_bare` という指示違反として別に数える。

## ゴールデンセット

| ファイル | 件数 | 構成 |
|---|---|---|
| `es.jsonl` | 30 | good 10 / mid 10 / bad 10 |
| `resume.jsonl` | 30 | good 10 / mid 10 / bad 10 |
| `interview-report.jsonl` | 30 | good 10 / mid 10 / bad 10 |

**全て合成データ。個人情報を含む実データは入っていない**（`docs/wiki/data-privacy.md` の方針）。
氏名は「学生A」、企業・学校名は「株式会社サンプル○○」「サンプル○○専門学校」のような
架空の名前で統一している。

### マニフェストの形式（1行1ケースの jsonl）

```json
{"id":"es-g01","target":"es","label":"good","input":{"es_text":"...","question_type":"ガクチカ","company_name":""},"note":"S/T/A/Rが全て揃い、廃棄額の変化を数値で示している"}
```

| フィールド | 内容 |
|---|---|
| `id` | 一意。`{target略称}-{g/m/b}{連番}` |
| `target` | `es` / `resume` / `interview-report` |
| `label` | `good` / `mid` / `bad` |
| `input` | target ごとの入力（下表） |
| `note` | **必須**。そのラベルを付けた理由。次にラベルを見直す人の根拠になる |

target ごとの `input`:

- `es`: `es_text`（必須）, `question_type`, `company_name`
- `resume`: `resume_text`（必須。**1行=1ブロック**として本番のOCRブロックに変換される）, `company_name`, `job_title`, `candidate_type`（**`new_grad` / `mid_career` のみ**。ルーブリックの重みをこの値で引くため、他の値だと本番と違う条件で測ることになる）
- `interview-report`: `transcript`（必須。`Interviewer: ` / `User: ` 行。`interview.BuildTranscript` と同形式）, `lang`

`transcript` の役割ラベルは必須。根拠の捏造チェック（`ValidateEvidence`）が
「受験者が言ったか」を見るため、役割が復元できないと面接官の質問文を根拠にしても検出できない。

### ラベルの付け方（良 / 中 / 悪）

3値に留めているのは、人がラベルを付け直したときに揺れない粒度にするため。
5段階にすると境界の判断が人によって変わり、「誰が測っても同じ数字」が崩れる。

判断は**書かれている内容だけ**で行う。書き手の努力や事情は見ない。

#### 共通の基準

| ラベル | 基準 |
|---|---|
| **good** | 状況・自分の行動・結果の3つが揃い、結果に**検証可能な具体（数値・期間・人数・固有名詞）**がある。自分が何を判断したかが読み取れる |
| **mid** | エピソードはあるが、3つのうち**1つが曖昧**。典型は「結果が『良くなった』だけで数値が無い」「数値はあるが自分の寄与が不明」「行動はあるがなぜそうしたかの理由が無い」 |
| **bad** | 抽象語・感想・誇張のみで、検証可能な具体が**1つも無い**。または質問に答えていない |

#### target ごとの追加基準

**ES添削（`es.jsonl`）**

- good: STAR（Situation/Task/Action/Result）が4つ揃っている。Resultに数値がある
- mid: STARのうち1つが欠けているか曖昧。よくあるのは Result の数値欠落
- bad: 「一生懸命頑張りました」「コミュニケーション能力があります」のような
  強みの名前だけ、同じ内容の繰り返し、どの企業にも当てはまる志望動機

**履歴書レビュー（`resume.jsonl`）**

- good: 職歴に期間・役割・成果があり、学歴/職歴/資格の年月に矛盾が無い
- mid: 一部の項目は具体的だが他が薄い。職歴の期間が書かれていない等
- bad: 記載がほぼ空欄、業務名の羅列だけ、または**学歴/職歴/資格の年月に矛盾がある**
  （在籍前の職歴、入学前の資格取得など。`rs-b02` `rs-b07` がその例）

**面接レポート（`interview-report.jsonl`）**

- good: 4問すべてで具体的なエピソードと数値を答え、苦労した点に対策と結果がある
- mid: 答えてはいるが具体性が薄い。数値はあるが自分の寄与が不明など
- bad: 「特にないです」「わかりません」のような短答、抽象語のみ、質問とずれた回答

#### 長さの扱い（既知の限界）

ラベルがスコアではなく**長さ**で当てられてしまうと弁別力の測定にならない。
そのため ES は good/mid/bad の文字数をなるべく揃えてある（bad も抽象語で
同じ長さまで書いてある）。実測の平均文字数:

| target | good | mid | bad |
|---|---|---|---|
| `es.jsonl` | 254字 | 224字 | 212字 |
| `resume.jsonl` | 363字 | 270字 | 172字 |
| `interview-report.jsonl` | 649字 | 539字 | 338字 |

履歴書と面接ログは差が残っている。**内容が薄い履歴書・短い面接回答は現実に短い**ため、
無理に揃えると入力が非現実的になる。ここは「長さも弁別の手がかりに入っている」ことを
承知の上で使う。長さの影響を切り分けたいときは、長さを揃えた追加ケースを足すこと。

### ケースを足す・直すとき

1. jsonl に1行追記する（`note` にラベルの理由を必ず書く）
2. `cd Backend && go test ./internal/aibench/...` で検証する
   （id重複・ラベル不正・必須フィールド欠落・件数とラベル構成・`note` の空を見ている）
3. **ケースを足したら過去の結果と数字を直接比べられない**。マニフェストのSHA256が
   変わるので `-diff` は警告を出す。比較したいときは追加前のマニフェストで測り直すこと

### 実データを使いたいとき

**実データはコミットしない。** 匿名化したものでも、このディレクトリには置かない。

1. リポジトリ外（例: `~/ai-eval-private/`）にマニフェストを作る
2. `-manifest ~/ai-eval-private/es-real.jsonl` で指定する（パスは任意の場所で動く）
3. 結果JSONもリポジトリ外へ出す（`-out`）
4. 匿名化は `docs/wiki/data-privacy.md` の方針に従う。氏名・学校名・企業名・
   連絡先・生年月日は置き換える。エピソード中の固有名詞（部活名・大会名・
   アルバイト先の店名）も個人を特定しうるので置き換える
5. 実データで測った数字を共有するときは「実データ / 非公開マニフェスト」と明記する。
   合成データの数字と混ぜて比較しないこと

## 指示違反の一覧

指示遵守率の分子になる「違反なし」の判定に使っている項目。
プロンプトが明示している約束だけを見ている。

指示遵守率は**全項目のANDで判定する**ため、systematic に起きる違反が1つあると 0% に
張り付く。値だけを見ずに、結果JSONの `violation_counts`（表示では破損率の横の内訳）で
どの項目が原因かを必ず確認すること。
（実測例: `resume` は gpt-4o-mini で `json_not_bare` が18/18回発生し遵守率0%になる。
本番は復旧処理で読めているのでユーザー影響は無いが、「JSONのみ」の指示は守られていない）

**共通**

| 違反名 | 内容 |
|---|---|
| `json_not_bare` | 「JSONのみ」の指示に反し、コードフェンスや散文で包まれていた |
| `summary_empty` | 要約が空 |

**`es`**（許容幅は `internal/aibench/target_es.go` の定数。動かすと遵守率も動く）

| 違反名 | 内容 |
|---|---|
| `feedback_length` | feedback が250字未満または700字超（プロンプトは「400字程度」） |
| `improved_text_ratio` | improved_text が元の100%未満または145%超（プロンプトは「110〜130%を目安」） |
| `company_fit_without_context` | 企業情報が無いのに企業適合度を返した（#1524違反） |
| `company_strategy_without_context` | 企業情報が無いのに企業対策を返した（#1524違反） |

**`resume`**

項目スコア（ルーブリック）の欠落・値域外・未知キーは違反ではなく**破損**（`schema_incomplete`）
として数える。本番も `ValidateResumeRubricScores` を通らなければ固定値を入れずスコアを
捨てる（#1529）ので、スコアが取れないこと自体が品質の欠落である。

| 違反名 | 内容 |
|---|---|
| `items_empty` / `items_over_limit` | items が0件、または8件超 |
| `item_missing_fields` | quote / message / suggestion のいずれかが空 |
| `severity_invalid` | severity が info / warning / critical 以外 |
| `quote_not_in_text` | **quote が本文に存在しない（捏造）**。空白と改行の差は無視して照合する |

**`interview-report`**

| 違反名 | 内容 |
|---|---|
| `scores_invalid` | 本番の `ValidateRubricScores` が弾く値（キー欠落・0〜5の外） |
| `strengths_count` / `improvements_count` | 2〜4件の指示に反している |
| `teacher_missing` | teacher が無いか総評が空 |
| `evidence_not_spoken` | **根拠が受験者の発話に基づかない（捏造）**。本番と同じ `ValidateEvidence` で照合する |
| `teacher_evidence_not_spoken` | 同じく教員向けの詳細根拠 |

捏造の照合は本番と同じ関数を呼んでいる（`interview.SpokenContent` +
`interview.ValidateEvidence`）。ハーネス側で別実装にすると、本番が弾く/弾かないの
境界とハーネスの数字がずれる。

**`evidence_not_spoken` は「引用になっていない」を数える指標である。** #1580 で照合が
内容語ベースになったため、発話の語彙を引き継がない抽象的な講評
（「論理的に筋道立てて説明できていました」等）は通らない。完全引用は1.000、
語彙を引き継いだ要約は0.667で通り、面接官の発言は0.154で落ちる（しきい値0.25）。
この境界は `TestゴールデンセットでEvidence照合が正しく分かれる` が固定している。

照合の実装が変わると同じ出力でもこの違反数が変わる。**照合を変えた前後の数字を
「モデルが悪化した」と読まないこと。** 比較できるのは照合が同じ実行同士だけである。

## 劣化の検知（`-diff`）

前回結果と比べて次のいずれかに当たると「劣化」として報告し、終了コード1になる。
閾値は `internal/aibench/report.go` にある。温度0.2〜0.4で回すため、同じプロンプトでも
実行ごとに数%は動く。緩めると気付けず、厳しくすると毎回赤くなる。

| 指標 | 劣化の条件 |
|---|---|
| 破損率 | 5ポイント以上増えた |
| 指示遵守率 | 5ポイント以上減った |
| 弁別力（順位相関） | 0.10以上下がった |
| 再現性（平均σ） | 0.05以上増えた |
| レイテンシ p95 | 1.2倍以上になった |
| コスト（1件） | 1.2倍以上になった |

target・マニフェストのSHA256・モデル名・件数が違う場合は警告を出す。
別の入力で測った結果を並べても意味が無いどころか、「改善した」という誤った結論を出す。

| `Backend/internal/aibench/aggregate.go` | 指標の集計 |
| `Backend/internal/aibench/call.go` | OpenAI の生HTTP呼び出し（リトライなし） |
| `Backend/internal/aibench/target_*.go` | 評価対象ごとの呼び出しと判定 |
| `Backend/internal/aibench/report.go` | 表示と差分 |

プロンプトはハーネスに写さず、本番の関数を呼んでいる。
写すと本文を直した瞬間に測っている対象が本番と別物になり、数字が判断材料にならない。

- ES: HTTP `POST /es/review`（プロンプトは `rag/services/es_review.py`）
- 履歴書: `resume.BuildReviewPromptFromText` / `resume.ReviewSystemPrompt` / `resume.ReviewModel`
- 面接レポート: `interview.BuildReportPrompts`

集計ロジックには LLM を呼ばないテストがある（`Backend/internal/aibench/*_test.go`）。
指標の計算が壊れても実行結果は返ってくるため、テストが無いと
「数字は出るが意味が違う」状態に気付けない。

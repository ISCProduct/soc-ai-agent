# Redis / ジョブキュー運用メモ（#617）

## 環境変数

| 変数 | 説明 |
|------|------|
| `REDIS_URL` | 例 `redis://localhost:6379/0`。未設定時はインメモリレート制限 + `go func` / in-process channel |

## ローカル

```bash
docker compose up -d redis
# Backend/.env に REDIS_URL=redis://localhost:6379/0
```

compose の `backend` サービスは `redis` に依存し、既定で `REDIS_URL=redis://redis:6379/0`。

## 配置方針

- Redis は **Backend と別コンテナ**（同梱しない）
- staging/prod は ElastiCache または別 ECS サービス推奨（サイドカー同一タスクは非推奨）

## ジョブ

| タスク | リトライ | 備考 |
|--------|----------|------|
| `email:*` | 5 | critical キュー |
| `interview:report` | 3 | default キュー / セッション単位で重複排除（`asynq.TaskID`） |

失敗はログ `[queue] task failed`。asynq の archive（DLQ）に保持。

`interview:report` は発話が0件のセッションで `ErrNoUtterances` を返し、リトライ対象になる（#1476）。
発話保存がネットワーク瞬断などで欠落した場合に、空レポートを「正常終了」として確定させないため。
リトライし切っても0件ならレポートは作らない（フロントのポーリングがタイムアウトし、生成失敗として見える）。

### 未生成レポートの再生成（#1476）

リトライを使い切る／フォールバックの channel worker で失敗する／`jobCh` が満杯で捨てられる、
のいずれでもレポート生成ジョブは失われる。`POST /api/interviews/:id/finish` は終了済みセッションを
再キューしない（#1019 の冪等性）ため、回復経路は次の1本だけ。

`POST /api/interviews/:id/report/regenerate`

- 終了済み（`status = finished`）かつレポート未生成のときだけ再投入し、`{"queued": true}` を返す
- 既にレポートがあれば何もしない（`{"queued": false}`）。無条件に再投入すると LLM 費用が二重に掛かり、生成中のレポートを上書きする
- 未終了セッションは 400、他人のセッションは 403
- フォールバックの `jobCh` が満杯でジョブを投入できなかった場合は 503。
  ここを 202 で返すと、フロントは存在しないジョブを3分ポーリングして同じタイムアウト画面に戻るだけになる
- フロントはレポート画面の「再試行」ボタン（ポーリングのタイムアウト／失敗後）から叩く

再生成リクエスト自体が失敗した（オフライン・401・500 など）場合、フロントはポーリングへ戻さず
レポート画面にエラーを出す。ジョブが入り直っていないのに「生成中」へ戻すと、
ユーザーは失敗を知らされないままもう一度3分待たされる。

#### 重複排除と回復の両立

レポートが保存される前に `finish` と `regenerate` が重なると、同じセッションで複数のジョブが走り、
LLM 費用が二重に掛かり、レポートが後勝ちで上書きされ、スコアの移動平均も二重に効く。
`interview:report` は `asynq.TaskID`（`interview-report-<session_id>`）でセッション単位に重複排除する。
重複投入はエラーではなく成功扱い（＝既にジョブが控えている状態）で、channel へのフォールバックもしない。

- `asynq.Unique` は使わない。ロックが「投入から TTL まで」しか効かず、
  TTL（=1回の実行上限）はキュー待ち＋最大3回のリトライを含まないため、リトライ待ちのジョブに重ねられる。
- `TaskID` は pending/active/scheduled/retry の全状態と衝突するので、ジョブが生きている間は重複を弾ける。
- `TaskID` は「終わったタスク」（`Retention` 24時間の completed、リトライを使い切った archived）とも
  衝突する。ここを素通しにすると唯一の回復手段である再生成が最大24時間塞がるため、
  衝突時は `asynq.Inspector` でタスクの状態を見て、**終わっているものだけ削除してから入れ直す**。
  結果、回復は決して塞がらず、生きているジョブの重複も起きない。

フォールバックの channel 経路（Redis 未設定・障害時）にも同じ単位の重複排除を入れている。
セッションIDを投入時に登録し、worker が処理を終えるまで保持する（処理中の再投入も弾く）。
失敗して終わればすぐ登録が外れるので、こちらも再生成は塞がらない。

## フォールバック

Redis 不通時:

- レート制限: フェイルオープン（許可）
- ジョブ: エンキュー失敗時は従来の `go func` / channel にフォールバック

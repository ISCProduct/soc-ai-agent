# スコアキャリブレーション調査・手順

## 現状と結論

チャット・適性検査の合成比率 `ChatWeight=0.5`、選考結果から算出するカテゴリ重み、面接スコア写像の係数はいずれも**較正済みではない**。根拠となる実績データが確認できるまで暫定値のまま扱い、推薦の妥当性を示す指標として説明しない。

Issue #1774 の調査時、接続できたローカル `app_db` は `user_weight_scores`、`user_application_statuses`、`assessment_results` がいずれも0件だった。staging / production のDBにはこの環境から接続しておらず、件数は未確認である。したがって現時点の判定は**較正可能性を確認できず、較正を実行しない**。本番・stagingのデータ所有者が承認した読み取り専用の集計で件数を確認すること。

### 現行レポート・処理の制約

- `/api/admin/score-validation/correlation` は `user_weight_scores` と選考結果をユーザーIDだけで結合し、応募時点とは異なるセッションや応募後のスコアも対応づけ得る。スコア帯ごとの通過率の差は統計的な相関係数ではない。
- 現行キャリブレーションはこのユーザー単位の結合からカテゴリ別通過率を作り、全カテゴリ平均との比を重みとして保存する。返却する `correlation` も重みから算出した近似値で、実測相関ではない。各カテゴリ5件という条件も統計的な較正可能性を保証しない。
- 保存された `ScoreCalibrationWeight` は現状マッチングには適用されない。これらのAPI結果を重み変更、相関の根拠、A/Bテストの成功判定に使わない。

## まず確認する集計

承認された環境ごとに、個人を識別できる値を出力せず次を集計する。ソース・カテゴリ別のスコア行数とユーザー数、ステータス別の応募数とユーザー数、`match_id` からセッションまで対応する応募数、各選考結果ラベル数、チャット・標準適性検査の両方を持つ人数を記録する。未確定・辞退・進行中などの件数も分け、通過ラベルに混ぜない。

単純な件数だけでは較正対象の件数にならない。応募とスコアの対応は `user_id` だけでなく `match_id` と `user_company_matches.session_id` を使って調べる。適性検査スコアは別セッションに保存されるため、マッチング時に使った値のスナップショットがなければ、後から「最新値」を結合して応募時点の特徴量を復元できない。staging / production の数値、抽出日、対象期間、ステータス定義、重複応募の扱いを調査記録に残す。

## 較正に必要なデータ

較正用の分析単位は**候補者×企業（応募）**とし、少なくとも以下を同一レコードとして再現できる必要がある。

- 応募・選考結果（結果の定義、最終確定時刻、進行中・辞退・未記録の区別）
- マッチング時点で実際に使った全カテゴリスコア、chat / assessment の内訳と欠損状態
- スコア・合成ロジック・重み・質問または検査テンプレートの各バージョンとスナップショット時刻
- `match_id`、応募企業・職種などの評価対象、および応募・スコア計算・結果確定の時刻
- 重複応募、同一候補者からの複数応募、結果未確定による打ち切りを識別できる情報

**最小件数を一律に「各カテゴリ5件」とは定めない。** 期待する効果量、通過率、検定力、許容する信頼区間幅を分析前に定めて必要数を計算する。複数カテゴリの同時評価、候補者内の応募相関、組織・職種ごとの差も考慮する。必要数に達しない、ラベルが偏る、または時点付きスコアを復元できない場合は較正不可と判定する。

## データが揃った後の較正手順

1. 対象集団・期間・結果ラベル・除外規則・主要評価指標と必要サンプル数を事前に決め、集計定義をレビューする。
2. 応募単位のスナップショットを作り、漏洩・重複・欠損・結果未確定を検査する。候補者が学習側と評価側にまたがらないよう分割し、将来期間のホールドアウトも確保する。
3. 学習データでのみ、適切な正則化を含む統計モデルを検討する。重みの推定値だけでなく信頼区間を示し、ベースラインとホールドアウトで識別性能・確率校正（例: Brier score、校正曲線）を比較する。カテゴリ・職種・選考段階などの偏りも確認する。
4. 推定値、対象データの期間・件数・ラベル定義、特徴量とロジックのバージョン、モデル手法・パラメーター、評価結果、承認者を一つの較正バージョンとして保存する。差が不確か、再現しない、または特定集団で悪化する場合は適用しない。
5. 承認後もまず限定的なシャドー評価を行い、基準を満たした場合のみ適用する。既存ユーザーのスコア再計算は自動で行わず、SOCAIAGENT-454 と連動して影響範囲・ロールバック方法を定める。

`ChatWeight` や面接写像係数は、上記のデータで比較可能な評価計画を別途定めるまでは固定の暫定値とする。**この手順書だけを根拠に係数を更新してはならない。**

## 変換式を変えるときのドライラン（#1528）

キャリブレーション（重み係数の調整）とは別に、
**履歴書・面接から `user_weight_scores` への変換式そのもの**を変えることがあります。
式を変えると既存ユーザーのスコア分布が動くため、適用前に新旧を並べて確認します。

```sh
cd Backend && go test ./internal/services/flywheel/ -run DryRun -v
```

DB へは一切書き込みません。入力（履歴書の総合スコアと critical 件数、
面接のルーブリックと発話量）の全域を掃くので、
既存行を読んで分布を取るより変化を漏れなく見られます。

出力例（抜粋）:

```
=== 履歴書レビュー → user_weight_scores ===
score critical | 旧(細部/コミュ/技術) | 新(細部/コミュ)
    0        0 | 書き込みなし          | 0/20
   50        0 | 書き込みなし          | 50/50
  100        0 | 加点 100/100/100     | 100/80

=== 面接レポート → user_weight_scores ===
rubric evidence文字数 平均回答文字数 ターン | 旧 | 新
     3              0              0      0 |  60 |  60
     3            200            120     10 |  60 |  65
```

evidence も発話統計も無い行が補正なし（`60`）なのは仕様です。
**記録の不備で下げない**（#1554）ため、どちらの欠損も中立扱いにしています。

変換式と各カテゴリの対応の根拠は
[スコアリング設計 §6.3](./scoring.md) と
`Backend/internal/services/flywheel/score_mapping.go` にあります。

この出力は `testdata/score_mapping_dryrun.golden` として固定されています。
キャリブレーション定数（`criticalPenaltyPerItem` / `evidenceFullRunes` /
`evidenceSignalWeight` など）を**意図して**変えたときは、
差分を確認した上で次のコマンドでゴールデンを更新してください。

```sh
cd Backend && go test ./internal/services/flywheel/ -run DryRun -update
```

**既存行は一括再計算しません。** 次のレビュー・面接から移動平均
（`既存*0.7 + 新*0.3`）で徐々に置き換わります。
このとき新値は ×0.3 され、`score` が int なので差分の整数化でさらに潰れます。
`delta == 0` になる範囲（既存60に対する新値59〜61）は書き込み自体をスキップするため、
`updated_at` も動きません。**ドライランの分解能がそのまま保存されるのは初回書き込みのとき**で、
2回目以降は1回の面接あたりの効きが弱くなります（繰り返せば収束します）。
詳細は [スコアリング設計 §6.3](./scoring.md) と #1560 を参照してください。

# School Career UI Design Skill

## 目的

このSkillは、学校の先生・学生が利用する就職活動支援システム `soc-ai-agent` のUI/UXを設計・実装するためのルールを定義する。

対象リポジトリ：

```text
ISCProduct/soc-ai-agent
```

フロントエンドの主要技術：

```text
Next.js 16
React 19
TypeScript
MUI 7
Lucide React
Recharts
Radix UI
```

このSkillでは、見た目の華やかさよりも、

- 分かりやすさ
- 操作の迷いにくさ
- 情報の優先順位
- 少ない操作回数
- 就職活動に必要な行動の分かりやすさ
- 教員による学生支援のしやすさ
- アクセシビリティ
- レスポンシブ対応

を優先する。

---

# 1. 基本原則

画面を作成するときは、いきなり実装しない。

必ず最初に以下を整理する。

1. 誰が使う画面か
2. 画面の目的
3. 最も重要な操作
4. 表示する情報
5. 情報の優先順位
6. ユーザーフロー
7. 必要なコンポーネント
8. PCレイアウト
9. スマートフォンレイアウト
10. Loading状態
11. Empty状態
12. Error状態

画面設計が整理できてから実装する。

---

# 2. 想定ユーザー

このシステムには主に以下の利用者がいる。

## 学生

主な利用目的：

- AIとの就活相談
- 企業推薦
- 企業情報閲覧
- 応募管理
- 面接管理
- 履歴書作成
- スケジュール管理
- 自分の就活状況確認
- 先生からのフィードバック確認

学生向けUIでは、

```text
管理する
```

よりも、

```text
次に何をすればいいか
```

を優先する。

---

## 教員

主な利用目的：

- 学生の就活状況確認
- 要フォロー学生の確認
- 未活動学生の確認
- 応募状況確認
- 面接状況確認
- 内定状況確認
- 学生個別情報確認
- コメント・支援

教員向けUIでは、

```text
誰を支援する必要があるか
```

を最優先にする。

---

## システム管理者

主な利用目的：

- 学生管理
- 企業管理
- アカウント管理
- マスタ管理
- システム設定
- データ管理
- 利用状況確認

管理者画面では情報密度と作業効率を優先する。

# 3. ロールごとの情報設計

学生画面は情報を詰め込みすぎない。

優先順位：

1. 次にやること
2. 締切
3. 面接予定
4. 応募状況
5. 推薦企業
6. 先生からのコメント
7. AI相談
8. 履歴・過去データ

### 推奨例

```text

────────────────────

────────────────────

・自社サービス

```

# 4. 学生向けUIルール

## 4.1 行動中心

画面上部には必ず、

```text
次にやるべきこと
```

を優先して表示する。

単純な統計値を最上部に並べない。

悪い例：

```text
応募数 12
閲覧企業数 48
AI利用数 31
お気に入り 7
```

良い例：

```text
明日14:00から面接があります

[ 面接対策をする ]
```

---

## 4.2 学生向けダッシュボード

基本構成：

```text
Header

Greeting

次にやること

締切

面接・予定

おすすめ企業

先生からのコメント

最近の活動
```

大量のカードを並べない。

KPIカードを使用する場合は最大4つ程度にする。

---

## 4.3 文言

学生向け画面ではシステム用語を避ける。

悪い例：

```text
応募ステータス変更
データ登録
レコード更新
Recommendation Result
```

良い例：

```text
応募状況を変更
企業を保存
内容を更新
おすすめ企業
```

---

# 5. 教員向けUIルール

教員向け画面では、

```text
対応が必要な学生
```

を最初に表示する。

推奨構成：

```text
就活状況

要フォロー
未活動
面接予定
内定

要フォロー学生一覧

学生検索

クラス・学科フィルター

学生一覧
```

---

## 5.1 要フォロー

以下のような条件を想定して表示する。

- 一定期間活動がない
- 応募企業がない
- 面接予定がない
- 不採用が続いている
- 締切超過
- プロフィール未完成
- 履歴書未完成

ただし、AIだけで重大な判断を確定しない。

表示例：

```text
最近14日間、活動がありません
```

推奨しない表現：

```text
就活意欲が低い学生です
```

---

## 5.2 教員向け一覧

表形式を基本とする。

例：

| 学生 | 学科 | 応募状況 | 面接 | 最終活動 | 状態 |
|---|---|---|---|---|---|
| 山田太郎 | 情報セキュリティ | 3社 | 1件 | 9/28 | 活動中 |
| 佐藤花子 | IT | 0社 | 0件 | 9/14 | 要確認 |

表には必要以上の列を表示しない。

詳細情報は個別画面で確認する。

---

# 6. AI機能のUI

AIが出した情報は、確定情報のように見せない。

悪い例：

```text
あなたに最適な会社です
```

良い例：

```text
あなたの希望条件との一致度が高い企業です
```

---

## 6.1 推薦企業

企業推薦には可能な限り以下を表示する。

- 企業名
- 業界
- 職種
- 勤務地
- 一致度
- 一致理由
- 元データ
- 出典
- データ取得日
- AI補完の有無

一致度だけで企業の価値を判断させない。

---

## 6.2 AI補完

AIが補完したデータには明示する。

例：

```text
AIによる補完情報
```

必要に応じて以下も表示する。

```text
この情報は公開情報をもとにAIが整理した内容です。
```

---

# 7. 企業カード

企業カードは情報を詰め込みすぎない。

推奨情報：

```text
企業名

業界
職種
勤務地

希望条件との一致度

一致している条件
・自社サービス
・東京勤務
・Webエンジニア

[ 詳細を見る ]
```

避ける：

```text
企業カード内に長文説明を全て表示
```

詳細情報は企業詳細画面で表示する。

---

# 8. 応募管理

応募画面ではステータスを明確にする。

推奨ステータス：

```text
検討中
応募予定
応募済み
書類選考
面接
内定
不採用
辞退
```

内部用のステータスコードを直接表示しない。

---

# 9. 面接画面

面接画面では、

```text
次の面接
```

を最優先にする。

表示項目：

- 企業名
- 日付
- 時刻
- 面接形式
- URLまたは場所
- 面接回数
- メモ
- 面接対策

例：

```text
ABC株式会社

一次面接

9月30日 14:00

オンライン

[ 面接対策をする ]
[ 詳細を見る ]
```

---

# 10. スケジュール画面

スケジュールは就活イベントを中心にする。

対象：

- 応募締切
- ES締切
- 説明会
- 面接
- 適性検査
- 学校イベント

色だけでイベント種類を表現しない。

必ずラベルやアイコンも使用する。

---

# 11. 履歴書画面

履歴書は長い1ページフォームにしない。

セクション単位で分割する。

例：

```text
基本情報

学歴

資格

自己PR

志望動機

スキル

確認
```

保存状態を明確にする。

例：

```text
保存済み
```

---

# 12. フォーム

フォームでは入力項目を必要最小限にする。

必須項目は明示する。

推奨：

```text
氏名 *

メールアドレス *

電話番号
```

エラーは入力欄の近くに表示する。

悪い例：

```text
入力内容に問題があります
```

良い例：

```text
メールアドレスの形式を確認してください
```

---

# 13. ボタン

ボタンには具体的な操作名を使用する。

悪い例：

```text
OK
実行
処理
登録
```

良い例：

```text
企業を保存
応募状況を更新
履歴書を保存
面接対策を始める
コメントを送信
```

---

# 14. 破壊的操作

削除や取消は通常操作と分離する。

例：

```text
[ 保存 ]

----------------

応募情報を削除
```

削除前には確認を行う。

---

# 15. Navigation

学生向けは複雑なナビゲーションを避ける。

候補：

```text
ホーム
企業を探す
応募
面接
スケジュール
AI相談
```

その他機能はユーザーメニュー等にまとめる。

---

## 教員

候補：

```text
ホーム
学生
就活状況
企業
スケジュール
```

---

## 管理者

管理機能数が多い場合はサイドバーを使用してよい。

# 16. MUI

既存のMUIを優先する。

新しいUIライブラリを安易に追加しない。

使用候補：

```text
Button
Card
Paper
Stack
Grid
Container
Typography
TextField
Select
Chip
Table
Tabs
Dialog
Snackbar
Alert
Skeleton
Avatar
Tooltip
```

---

# 17. アイコン

原則として既存のアイコンライブラリを使用する。

利用候補：

```text
@mui/icons-material
lucide-react
```

アイコンだけのボタンは避ける。

アイコンだけの場合は、

```text
aria-label
Tooltip
```

を設定する。

---

# 18. カード

カードを大量に使わない。

カードを使う理由：

- 情報のまとまりが明確
- クリック可能な単位
- 他の情報との分離が必要

単に枠を付ける目的では使用しない。

---

# 19. 色

色だけで状態を伝えない。

例：

悪い：

```text
赤 = 未提出
緑 = 完了
```

良い：

```text
● 未提出
✓ 完了
```

色は補助として使用する。

---

# 20. Typography

本文は原則として、

```text
16px前後
```

を基準にする。

重要情報は階層をつける。

例：

```text
Page Title

Section Title

Main Information

Supporting Information
```

文字サイズを過剰に増やさない。

---

# 21. レスポンシブ

最低限以下を確認する。

```text
375px
768px
1024px
1440px
```

学生はスマートフォン利用を重視する。

---

## Mobile

スマートフォンでは、

- 横スクロール表を避ける
- タップ領域を広くする
- ボタンを押しやすくする
- 情報を縦方向に並べる
- 重要操作を画面下部に配置することも検討する

一覧表はカード表示への切り替えを検討する。

---

# 22. アクセシビリティ

最低限以下を確認する。

- キーボード操作
- focus表示
- aria-label
- label
- コントラスト
- 色だけで状態を表現しない
- アイコンのみの操作を避ける
- 適切なHTML要素
- 見出し構造

---

# 23. Loading

データ取得中は画面全体を真っ白にしない。

Skeletonを優先する。

例：

```text
企業一覧 Loading
→ 企業カードSkeleton

学生一覧 Loading
→ Table Skeleton
```

---

# 24. Empty State

データがない場合は理由と次の操作を表示する。

悪い：

```text
データがありません
```

良い：

```text
まだ応募企業がありません。

気になる企業を探して応募候補に追加してみましょう。

[ 企業を探す ]
```

---

# 25. Error State

エラー表示では、

- 何が起きたか
- ユーザーが何をすればいいか

を表示する。

例：

```text
企業情報を取得できませんでした。

通信状態を確認して、もう一度お試しください。

[ 再読み込み ]
```

---

# 26. Dialog

モーダルを乱用しない。

以下の場合のみ使用する。

- 削除確認
- 短い編集
- 補助情報
- 画面遷移するほどではない操作

長い入力フォームは独立ページにする。

---

# 27. デザインの禁止事項

以下のようなAI生成UIを避ける。

- 大量のKPIカード
- 紫系グラデーションの多用
- 不要なGlassmorphism
- 過剰な影
- 過剰な角丸
- 意味のないアニメーション
- 意味のないアイコン
- 情報をカードに分割しすぎる
- 大きすぎる見出し
- LPのような業務画面
- 装飾目的のグラフ

---

# 28. グラフ

グラフは、

```text
意思決定に必要か
```

を確認してから使用する。

教員画面では以下は利用価値がある。

- 内定率推移
- 応募状況
- 面接状況
- 学科別進捗

学生画面ではグラフを増やしすぎない。

---

# 29. 既存画面

対象画面例：

```text
/applications
/interview
/results
/resume
/schedule
/chat-history
/profile
/company
/company-portal
/admin
```

既存画面を変更するときは、

```text

```

を確認する。

1画面だけ独自デザインにしない。

---

# 30. 実装ルール

既存コンポーネントがある場合は再利用する。

実装前に以下を確認する。

```text
frontend/components
frontend/app
frontend/styles
```

類似コンポーネントを新規作成しない。

---

# 31. コンポーネント分割

巨大なpage.tsxを避ける。

例：

```text
applications/
├── page.tsx
├── components/
│   ├── ApplicationCard.tsx
│   ├── ApplicationFilter.tsx
│   ├── ApplicationStatusChip.tsx
│   └── EmptyApplications.tsx
```

ただし、細かく分割しすぎない。

再利用性または可読性が高まる場合のみ分割する。

---

# 32. Design Token

可能な限り、

```text
Theme
spacing
palette
typography
shape
```

を利用する。

ページごとに色やmarginを直接設定し続けない。

# 33. 画面作成フロー

新しい画面を依頼された場合は次の順序で進める。

## Step 1

対象ユーザーを特定する。

```text
Student
Teacher
Admin
```

## Step 2

画面目的を1文で定義する。

例：

```text
学生が次の就職活動を迷わず確認できる画面
```

## Step 3

最重要操作を決める。

例：

```text
面接対策を開始する
```

## Step 4

情報優先順位を決める。

## Step 5

PC / Mobileレイアウトを考える。

## Step 6

Empty / Loading / Errorを設計する。

## Step 7

既存コンポーネントを確認する。

## Step 8

実装する。

## Step 9

アクセシビリティを確認する。

## Step 10

レスポンシブを確認する。

# 35. レビュー

実装後に以下を確認する。

## UX

- 次に何をすればいいか分かるか
- 不要な情報がないか
- 操作数が多すぎないか
- ボタン名が具体的か
- 状態が理解できるか

## UI

- 余白が統一されているか
- Typographyが統一されているか
- 色が統一されているか
- カードを使いすぎていないか

## Responsive

- Mobileで崩れていないか
- 横スクロールが発生していないか
- ボタンが押しやすいか

## Accessibility

- label
- aria
- keyboard
- focus
- contrast

# 36. 最重要ルール

このシステムで最も重要なのは、

```text
Student:
次に何をするべきか分かる

Teacher:
誰を支援するべきか分かる

Admin:
効率よく管理できる
```

という状態を作ることである。

見た目を綺麗にすること自体を目的にしない。

利用者の行動を分かりやすくすることを目的にUIを設計する。
